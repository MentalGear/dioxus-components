top layer
A clipping/stacking fixture pairing Tooltip, HoverCard, and Popover with native <div popover>/<button popovertarget> references for the Phase 4.4 top-layer oracle.
dx components add top_layer
Clipping escape
Every trigger below sits inside #clip-box, an ancestor with overflow: hidden; height: 60px; transform: translateZ(0). Each content panel sets an explicit min-height: 100px, taller than the clip -- open one and it should render fully visible outside the clip (WHATWG HTML §popover, top layer), not cut off at 60px.

Light dismiss, Escape, and stacking
The red panel is a high-z-index sibling positioned where each popover opens. Opening a popover="auto" (or a non-modal Popover) should render its content above that sibling (top layer stacking). Clicking elsewhere, or pressing Escape, should close it and sync back to data-state on the root/trigger -- the Rust signal must never strand.

Toast top-layer stacking (Migration A slice 3/3, final)
The small red panel is a high-z-index sibling pinned to the same fixed viewport corner the toast below will render at. Toasts never light-dismiss and never anchor to a trigger -- ToastProvider's region is `popover="manual"` purely so it always paints in the top layer, above whatever else is on the page (top-layer stacking, the same rule as the section above). Click the trigger to add a toast and cover the sibling.
Point-positioned vs. anchored scroll behavior (Migration A slice 2/3)
Both controls below sit normally in-flow (no clip ancestor, plenty of room on every side) so a modest scroll cannot itself cross a viewport-edge flip threshold -- these rules aren't about flipping (Rules 5-7 already cover that), they're about what happens to already-open content while the page scrolls. ContextMenu opens at a raw click point with no anchor -- pre-migration behavior (measured, then preserved by this migration) is that its content stays at the click's viewport-relative position, i.e. it does not move on screen as the page scrolls underneath it (same as a native OS context menu). Menubar's content, by contrast, is anchored to its own trigger (like DropdownMenu's Rule 8 case) and must keep tracking that trigger's position through a scroll.
Scroll test: right-click here
Near-viewport-edge flip (CSS position-try-fallbacks)
W3C CSS Anchor Positioning's position-try-fallbacks (spec) -- a CSS-spec citation, not WHATWG HTML, unlike the rest of this fixture; see the oracle spec's header for why this rule still lives in this tier-2 file. Every trigger below is pinned by fixed positioning right at a viewport edge, with its preferred side pointing off-viewport -- the bottom row's triggers request side="bottom" while sitting a few pixels from the bottom edge; the right column's request side="right" a few pixels from the right edge -- so content can only render fully on-screen by flipping to the opposite side on the relevant axis. A native <div popover> + position-try-fallbacks reference sits in each row/column too: the browser's own implementation of the identical spec feature, no library code involved (CALIBRATION).

Native <dialog> clipping escape (Phase 4.2)
The modal Dialog below sits inside #dialog-clip-box, the same overflow: hidden; height: 60px; transform: translateZ(0) ancestor as the section above. Its content is taller than the clip, so it must render fully visible outside it -- same top-layer rule, now for showModal() rather than popover=.
Native dialog reference content for the clipping-escape rule.
Native <dialog> background inertness (Phase 4.2)
While the alert dialog below is open, the background button/input here must be behaviourally inert: a real click must not reach the button's handler, and calling .focus() on the input directly must not move document.activeElement. (Chromium does not reflect this onto Element.inert for <body> -- docs/phase4-spike-findings.md -- so this fixture is measured behaviourally, not via that property.) Uses AlertDialog, not Dialog, deliberately: Dialog's own backdrop-click dismiss (dialog.spec.ts) would otherwise close the dialog the instant a background click lands outside it, which is a correct interaction but confounds this specific probe -- AlertDialog never light-dismisses, so it stays open through the whole check.

Native <dialog> modal Popover (two-engine completion)
The modal Popover below (default is_modal) now renders a real <dialog> opened with showModal() on the web arm, driven by the same open-driver/close-sync/backdrop-dismiss trio as modal Dialog -- except, unlike Dialog, a modal Popover stays anchored to its own trigger rather than viewport-centered. Three checks share the #popover-modal-clip-box/inertness/anchor sub-fixtures below: clipping escape (same overflow: hidden ancestor as the plain-Dialog case above), background inertness (click/focus must not reach the background button/input), and trigger-anchored placement -- the anchor trigger sits pinned near the top-left viewport corner, far from the viewport center, so a viewport-centered showModal() (the UA default this migration must override) would measurably disagree with a trigger-anchored one.
