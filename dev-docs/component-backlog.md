## Command palette — plan (2026-09-03)

**Ground truth this plan builds on** (read from source, not assumed):

- **`Dialog`** (`primitives/src/dialog.rs`) — modal web arm renders a real `<dialog>` driven by `showModal()`/`close()` (`use_dialog_open_driver`/`use_dialog_close_sync`, `primitives/src/lib.rs`), with rect-based backdrop dismiss (`use_dialog_backdrop_dismiss`) and native focus trap/restore/inertness supplied by the platform. `DialogRootProps` exposes `is_modal` (default `true`), controlled/uncontrolled `open`, and `id`. This is the shell `CommandDialog` wraps.
- **`Combobox`** (`primitives/src/combobox/`) — `Combobox<T>` root holds `ComboboxContext` (`selectable`, `query`/`set_query`, `filter`, `input_id`); `ComboboxInput` is a real `<input role="combobox">` driving `aria-activedescendant`/`aria-expanded`/`aria-controls`, with its own Arrow/Home/End/Enter/Escape keydown handling; `ComboboxList` renders the listbox and, on the web arm, promotes itself to the top layer via `popover="manual"` (`ComboboxListRendered`, `combobox/components/list.rs`) — **not** `auto`, because `auto`'s WHATWG light-dismiss closes the list on *any* outside pointerdown, including ones this component's own supported patterns rely on staying open across (documented at length in that file); `ComboboxOption` is `role="option"` wired through `collection_item`/`use_selectable_option`; `ComboboxEmpty` renders when `ctx.has_visible_options()` is false. Filtering is a caller-supplied `Callback<(String, String), bool>` (`combobox::default_combobox_filter` does a case-insensitive substring match); `select/text_search.rs`'s weighted-Levenshtein `best_match`/`normalized_distance` is the more sophisticated scoring this repo already owns (built for `Select`'s typeahead), a candidate for a fuzzier `Command` filter without inventing new matching logic.
- **`SelectGroup`/`SelectGroupLabel`** (`primitives/src/select/components/group.rs`) — the grouping pattern `Combobox` lacks entirely: `SelectGroup` renders `role="group"` with `aria-labelledby` pointed at a `SelectGroupContext.labeled_by` signal that `SelectGroupLabel` sets via `use_effect` on mount. This is the shape `CommandGroup`/`CommandGroupLabel` port.

**The plan:** a new `command` primitive module, composed from what exists rather than built from scratch —

- `Command` = `Combobox` rendered with an **inline, always-open list**, not a popover. Concretely: a mode (see the open question below) that makes `ComboboxList`'s web arm skip `popover="manual"`/`use_popover_shown_while_mounted`/the anchor-positioning fallback entirely and render as a plain in-flow `div[role="listbox"]` (i.e., the same shape `ComboboxListRendered`'s `#[cfg(not(feature = "web"))]` arm already renders unconditionally today) — a command palette's list is always visible while the dialog is open, so top-layer promotion, anchoring, and light-dismiss are all solving a problem `Command` doesn't have. `ctx.selectable.open` would need to default to (and effectively stay) `true` for as long as `Command` is mounted, rather than tracking focus/blur the way `Combobox`'s popover-list does.
- `CommandGroup`/`CommandGroupLabel` — ported from `SelectGroup`/`SelectGroupLabel`'s exact shape: `role="group"` + `aria-labelledby` wired from a mount-time `use_effect`, adapted to whatever `Command`'s listbox context type ends up being (see open question).
- `CommandEmpty` — `ComboboxEmpty`'s shape (render when no visible options), adapted to `Command`'s context/render-gate.
- `CommandItem` — `ComboboxOption` plus an optional `shortcut` slot: a presentation-only child element (no keyboard binding of its own — `cmdk`'s shortcut hints are visual labels, not the thing that fires the action; a real global keyboard-shortcut dispatcher, if ever wanted, is a separate, unscoped feature).
- `CommandDialog` = `Dialog` (`DialogRoot` + `DialogContent`) wrapping `Command`, with initial focus placed on the input rather than the platform's default first-focusable-element behavior — `showModal()`'s own focus algorithm (first `autofocus` element, else the dialog itself) means the input needs `autofocus` or an explicit initial-focus effect; confirm which by execution once `Command` exists, since `ComboboxInput` today never `autofocus`es on mount (nothing has needed it before).

**Oracle first**, per this repo's definition of done: the APG **combobox (editable, list autocomplete)** pattern rows — this repo's existing `Combobox` is presumably already calibrated against the vendored APG combobox reference (`playwright/oracle/reference/`); `Command`'s oracle should be that same rule set re-run against `Command`'s inline-list subject, plus this repo's existing native-`<dialog>` rules (`oracle/tier2-html/native-dialog.spec.ts`) for the dialog shell — clipping escape, background inertness, Escape/close sync, focus restore, nested-dialog close order. Axe at open (matches the row-34 axe-coverage convention — a scan at the default/open state, not just at rest). No new rule class needed; `Command` inherits both existing rule sets rather than earning a bespoke tier-3 one.

**Effort: S–M** (per the 2026-09-03 re-rating — down from the original harvest's "P2, M–L" now that `Dialog`'s native-modal machinery and `Combobox`'s top-layer/anchor-fallback plumbing both already exist; `Command` mostly needs *less* of what `Combobox` does, not more).

**References — read-never-vendor** (per `lifting-from-forks.md` §1, neither is a candidate for lifting):

- `dignifiedquire/dx-components` `primitives/src/command.rs` (Dioxus) — entangled with that fork's own `popper.rs`/`focus_scope.rs`, which this repo doesn't have and isn't porting (Shape C territory per `lifting-from-forks.md` §3, if ever taken at all — read for shape only).
- `rust-ui/dioxus-ui` `command.rs` (Dioxus 0.7 + Tailwind v4, `app_crates/registry/src/ui/command.rs`) — filtering and `aria-selected` state are driven by injected vanilla-JS strings outside Dioxus's reactive model; **behaviour not to be taken** (same caveat `component-backlog.md`'s NEXT section already carries for this fork's Command/Drawer). Its shape/group/shortcut markup conventions (a `cmdk`-style `Command`/`CommandGroup`/`CommandItem`/`kbd`-tag shortcut slot) are fine to look at.

**Open design question — one, with a recommendation:** does the inline, always-open list live *inside* the `Combobox`/`ComboboxList` primitive as a mode (e.g. a `display: ReadSignal<ComboboxDisplay>` prop on `Combobox`/`ComboboxList` that picks popover-vs-inline rendering), or is `Command` a sibling module that composes `Combobox`'s context directly (its own `CommandList` reimplementing `ComboboxList`'s render-gate/collection wiring without the popover branch, reusing `ComboboxContext`/`ComboboxOption`/`use_selectable_option` as-is)?

*Recommendation: sibling module.* `ComboboxListRendered`'s web arm is already carrying real complexity specific to the popover shape — `use_popover_shown_while_mounted`'s animate-out-race avoidance, the anchor-positioning fallback, the `dx-anchor-combobox` `@supports`-scoping marker class, the `auto`-vs-`manual` light-dismiss reasoning documented at length in that file. A mode flag would force every one of those code paths to become conditional on a prop that's `false` for exactly the caller (`Command`) that needs none of them, for no shared benefit — `Command`'s list has no anchor, no top-layer promotion, and no light-dismiss decision to make (the dialog shell owns dismissal). A sibling `CommandList` that skips straight to `ComboboxListRendered`'s existing `#[cfg(not(feature = "web"))]` shape (plain in-flow `div[role="listbox"]`, unconditionally, on *both* targets) is a small, legible file, not a fork in an already-intricate one — the same "read the fork's approach, write it against this codebase's own abstractions" call `lifting-from-forks.md` §3 (Shape C) recommends generally. It also keeps `Combobox`'s own test surface untouched: no new prop for `combobox.spec.ts` to have to prove is a no-op in the popover case.

## Recommendations

1. **The nine styled-only components have landed (2026-09-04, row 27); Command has now landed too (2026-09-14, this row).** They needed no accessibility engineering at all, which is exactly why they went first; Command turned out to be exactly the "cheapest primitive-needing win" this row predicted — `Dialog` and `Combobox`'s own underlying `crate::selectable`/`crate::listbox`/`crate::collection` layer carried essentially all of it, confirming by execution the plan's prediction that Command "mostly needs *less* of what Combobox does, not more": no popover, no top-layer promotion, no anchor positioning, no light-dismiss decision. One open question from the plan resolved by reading rather than assuming: `combobox::ComboboxContext` turned out to be `pub(super)` (private to that module tree), so `Command` composes the same `pub(crate)` infrastructure `Combobox` itself is built from, via its own small `CommandContext`, rather than the `ComboboxContext` type directly — see `primitives/src/command.rs`'s module doc for the full reasoning. See `dev-docs/backlog.md`'s "Fresh-session order" item 6 for the session account.
   **Addendum, 2026-09-14 — first real-browser `command.spec.ts` run (Chromium, `dx run --web --release`) found two real defects, not flakes, both fixed same day:**
   - **`aria-dialog-name` axe violation at "dialog open".** `dialog.rs`'s `DialogRoot` always wires the dialog's `aria-labelledby` to a `DialogTitle` id regardless of whether a `DialogTitle` is ever rendered (every `*Dialog`-family consumer in this repo — `Dialog`, `AlertDialog`, Sidebar's mobile `Sheet` — supplies one; this repo has no auto-defaulting convention to fall back on). The Command demo (`preview/src/components/command/variants/main/mod.rs`) omitted one, so `aria-labelledby` pointed at a non-existent element. Fixed by rendering a visually-hidden `dioxus_primitives::dialog::DialogTitle` inside the demo's `CommandDialog` (new `.dx-command-sr-only` class in `style.css`, the same shape `.dx-sidebar-sr-only` already uses for Sidebar's mobile `Sheet`), and by adding the same title to `primitives/src/command.rs`'s own `CommandDialog` doc example so it stops modeling the omission for the next reader.
   - **One `command.spec.ts` test (`types to filter, arrow-navigates, and selects with the keyboard`) timed out in `page.goto` at 5 minutes in the original run.** Reproduced by construction, not guessed: isolating just that test with `--repeat-each=5` across 2 Playwright workers on this sandbox's 4-core VM reproduced a 3.4-minute `page.goto` (still short of the 5-minute cap) on each worker's *first* navigation, dropping to ~13-14s on every subsequent test the same worker ran; running the identical test with `--workers=1` (no concurrent Chromium instance) never exceeded ~14s even cold. `curl` timings against the dev server confirmed every asset (HTML, the ~54KB JS loader, the ~6.75MB release-mode `.wasm`) is served in single-digit milliseconds, ruling out the server. The mechanism is client-side: `<script type="module" async>` still gates the `load` event on finishing execution, which awaits streaming-compiling and instantiating the ~6.75MB release-opt `.wasm`; under this sandbox's 4 CPU cores, two or more Playwright workers cold-compiling that same bundle at once (all nine `command.spec.ts` tests, and every other spec file, share the one SPA bundle) contend for CPU badly enough to push one unlucky worker's first navigation past 5 minutes, while causing zero symptom in any of the test's own Rust/TS logic (the hang is entirely inside `page.goto`, before any interaction runs). Concluded, with the evidence above, to be pure sandbox CPU-contention flakiness on this specific test's cold-navigation draw, not a product defect — nothing in `primitives/src/command.rs` or the demo was changed for this half of the fix. Verification: the full `command.spec.ts` (9 tests) passed twice in a row (9/9, 1.3m; then 18/18 across `--repeat-each=2`, 2.4m), including the previously-timing-out test finishing in ~13.9s both times.

One design decision worth recording per component, each cited in its own module doc or commit: **Table** merges a caller's class with each element's own `dx-table-*` class via `merge_attributes` rather than clobbering it (commit `724bfee`'s construction, still the standing pattern every new primitive should follow, not a one-off). **Data Table**'s `DataTableColumnHeader` always renders `translate` property, not `transform`: a `forwards`-held entrance `@keyframes` animation outranks even an inline `transform` for as long as it applies — the whole time the drawer is open, which is the only time a drag can happen — so `translate` (which composes with `transform` instead of competing for the same cascade slot) was the only way to get pointer-tracked movement and the entrance animation working at once. **Navigation Menu** is a new primitive, not an extension of `Navbar`: shadcn's disclosure-based site nav (plain links + `button[aria-expanded][aria-controls]` triggers, no reworking `Navbar` to serve both would have repeated the row-52/53 menu-consolidation duplication this repo already rejected once. **Resizable**'s handle `aria-orientation` is the *inverse* of the panel group's own layout direction: the APG Window Splitter pattern's Keyboard Interaction prose calls a Left/Right-moved splitter "vertical" (a vertical bar dividing side-by-side panes), matching this crate's existing `Separator` semantics (horizontal = a horizontal line) rather than the group's own `data-orientation`.
