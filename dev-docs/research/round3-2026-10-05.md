## 1. The modal close glitch (row 141)

**Report (owner, 2026-10-05).** Dialog close "glitches"; a right or left Sheet "changes size" while closing; the Drawer "glitches" on close. Reproduced on the HOME page only.

**Root cause.** `use_dialog_open_driver` (`primitives/src/lib.rs`) called `dialog.close()` the instant `open` went false. A native `close()` removes the dialog from the top layer in one frame. Outside the top layer a `position: fixed` box is no longer resolved against the viewport but against the nearest ancestor with layout containment, and is clipped by that ancestor's paint containment. On the home page that ancestor is the demo's `.dx-component-card`, which round 2 gave `content-visibility: auto`. The component pages have no such ancestor, which is how earlier verification missed it. `transition: overlay allow-discrete` kept the dialog in the top layer in Chromium only, and only until that transition ended, not in step with the panel's own exit; Firefox and Safari snapped.

**Measured (mid-slide, home page):**

| Surface | Layout box while open | Layout box once out of the top layer |
|---|---|---|
| Sheet (side) | 384 x 800 | 384 x 256 |
| Drawer (bottom) | 1265 x 346 | 1105 x 205 |

**Construction.**

- The shared driver keeps the dialog open until its own animations and its `::backdrop`'s have settled, bounded by `DIALOG_EXIT_TIMEOUT_MS` (1500 ms), then calls `close()`. A generation counter (`dialog.__dxDialogGen`) guards a reopen during the wait.
- `transition: overlay allow-discrete` is gone from the stylesheets, so the mechanism no longer depends on a Chromium-only feature. `dialog:not([open]) { display: none }` hides it between exit and mount.
- Consumers are derived from source (`playwright/modal-consumers.ts`): dialog, alert_dialog and popover call the driver; sheet, drawer and command compose `DialogRoot`. A test fails when a component composes a modal and has no entry, or an entry is stale. The modal Popover's web arm used to carry its own deferred-close driver and now calls the shared one, so the deferred close has one implementation; `lib.rs` is the only primitive that calls `showModal()`.
- Oracle `modal-exit.spec.ts` with `assert-modal-exit.ts` (and `assert-backdrop-fade.ts`): (1) a dialog is never rendered outside the top layer (`display !== none` implies `:modal`); (2) its layout box is constant for every rendered frame, so the exit is `transform`/`opacity`/`translate` only; (3) `close()` really waited: the `close` event arrives at least as long after `data-state` flipped to `closed` as the longest running animation (slack 40 ms). 2 and 3 are measured in browser events, not frame counts, so they hold on a starved debug main thread (row 115's lesson).

**The scroll lock premise was wrong.** The lock was assumed to release at the `open` flip. It released at unmount, about 250 ms after `close()` (`use_animated_open`'s hold). It now releases on the dialog's own `close` event: after the exit animation, before unmount. `listener-inventory.spec.ts` test 3 slows the exit to 1.2 s and asserts the page does not scroll and the wheel is cancelled while `dialog[open]` is still there, then scrolls once it has closed.

**Drawer drag (found in the same pass).**

- Upward drag closing: a press on the handle that ended over the `::backdrop` was read as a backdrop click. `use_dialog_backdrop_dismiss` now requires the PRESS to have started on the backdrop too; a dialog-wide fix, not a drawer one.
- Flick velocity was the displacement between the last two samples over effect-run times (floored at 1 ms), so on a busy main thread a slow drag read as a fling (the old test closed the drawer about 1 run in 3). It now uses the events' own `timeStamp`s over the last 100 ms, needs at least 10 px of travel to count as a flick, and applies a 25 % distance rule, a rubber band, and a snap-back on `pointercancel`. The whole gesture is one real-DOM script (`GESTURE_JS`), and orientation is applied once.

**Verification scope.** Chromium only (this sandbox has `chromium-1194` and no Firefox or WebKit). The cross-browser claim ("Firefox and Safari now get a real exit") rests on the construction, not an executed run; the proof on the other engines is row 4's.

Related, same round: the `overlay` prop (default `true`, Popover default `false`) is a `:where(dialog[data-dx-overlay="off"])::backdrop { ... !important }` rule in the theme; `:root { color-scheme: light dark }` with `html[data-theme]` pinning it, and native Select options use the popover tokens so the dark popup is dark. Spec `overlay-switch.spec.ts`.

## 2. First paint and stylesheet delivery

**Report (owner, 2026-10-05).** On a component page, first load shows a white or light version of elements before the dark or real style arrives, and shifts layout (example `/component/field/`); "Hydration?".

**Verdict, measured on the release SSG build of `001a5f0`: not hydration and not the theme.**

- Hard load is right: the JS-disabled page and the hydrated page have 0 differing computed styles over `main` in light and dark, hydration inserts no stylesheet, CLS is 0.0001, and the pre-paint script has set `data-theme` before the first paint.
- The defect is component CSS arriving late with UA defaults. Each component links its sheet with `document::Link` at its render point. The SSR head carries the sheets of what the SSR rendered, so a hard load is fine. A client-side navigation, or a popover's first open, renders FIRST and inserts its `<link>`s into a document that has already painted. A `<link>` added after `<body>` exists is not render-blocking (HTML spec: render-blocking elements can only be added while the document allows it; `blocking=render` on a late link measured as a no-op).
- Measured on 8 of 8 component pages: 5-10 late sheets, 150-270 ms of unstyled content at +100 ms of CSS latency, CLS 0.02-0.08; white `<input>`s (rgb(255,255,255), 2px border, radius 0), `.dx-field { display: block }`, then the reflow and a `transition: background-color` from white to dark.
- The date picker's first-open glitch is the same class: the calendar sheet is inserted when the popover content first mounts (UA-grey 2px-bordered day buttons, 207 px tall, then 280 px styled).

**Construction.** `scripts/ssg-css-bundle.mjs`, run by `scripts/build-ssg.sh` (guard 4b, on by default; `--no-css-bundle` is for before/after measurements only), puts ONE render-blocking `<link data-dx-css-bundle data-covers="...">` in every page head: 77 component sheets, 31 KB gzipped, in all 93 prerendered heads, after the four global sheets (`main`, `dx-components-theme`, `dx-effects`, `theme-presets`). The set is the union of every prerendered page's stylesheet links plus every project sheet in dx's asset manifest, so a new component is covered the day it lands. `preview/src/eager_head.rs` skips a link whose file is in `data-covers`, so a client-side navigation inserts nothing; the per-component `document::Link`s stay in the wrappers (that is what `dx components add` copies).

**Cascade order.** Per-route sheets were ordered by render order; a bundle has one order, and it must not flip results (bundling in first-appearance order flipped Field's label from 12.8 px to 14 px, caught by the oracle). The bundle order agrees with as many pages' own head orders as it can (pairwise votes, then local search). **208 of 2943 sheet pairs are ordered both ways on different pages**: route-and-history-dependent cascade that already existed. `scripts/compare-ssg-styles.mjs` compares a `--no-css-bundle` build with a bundled one over every route with JS disabled, light and dark: 82 of 83 routes identical in both schemes; the one difference was the HOME page's Field label (14 px by the gallery's own order, 12.8 px on the Field page and, with the bundle, everywhere). That is the instance that led to row 170.

**Guards.** Oracle `playwright/oracle/tier2-html/first-paint-styles.spec.ts` (160/160 on a bundled release build): the bundle is in every head after the four globals; hard-load parity; client-side navigation to every component has settled styles in its very first state, no uncovered sheet inserted, CLS about 0; the date picker's calendar is styled the moment it mounts; an explicit theme is on `<html>` before first paint; the detector is not blind. Tests 1, 3 and 4 are red on a build without the bundle. Static gate `scripts/check-css-delivery.sh` (bundler present, build runs it, deploy never disables it, `eager_head` still skips covered links, the font preloads are intact). DatePicker links the calendar CSS eagerly, as ColorPicker (input CSS) and Sidebar (sheet CSS) do.

**Font CLS.** Preloading the latin Geist and Geist Mono woff2 files with `display=optional` (a shift-proof pair; either alone is not): `/component/form/` 0.117 to 0.000, `/component/carousel/` 0.048 to 0.

## 3. The second-range hang (date picker, a latent defect on HEAD)

Completing a SECOND range in one page froze the tab (debug and release; hash-ordered wake order made it reproduce on some builds and some opens and not others, which is why no single run cleared it).

**Trace.**

1. `DateRangePickerContext::set_range` is a guarded setter ("only report if it differs") called from `DateRangePickerInputValue`'s sync-up effect (segments to range). It compared with a TRACKED read of the controlled range.
2. The tracked read subscribed the sync-up effect to the parent's value. Every change the parent makes to the range, including the one a calendar click has just reported upward, woke the sync-up effect.
3. When sync-up ran BEFORE the sync-down effect (range to segments) had copied the new range into the segment signals, it read the PREVIOUS range from the segments, found it differed from the parent's value, and reported the stale range back up.
4. The parent applied it one render later; sync-down copied it into the segments; sync-up reported that; the two ranges alternated forever. A wasm loop that never yields to the browser.

**Fix and gate.** `set_range` compares through `.peek()` (as `DatePickerContext::set_date` already did): a setter exists to emit, never to subscribe its caller. `scripts/check-self-subscribing-effects.sh` was blind to this shape (the effect writes nothing itself; the write is the callback), so it gained a second check by construction: for every `fn` with a `self` receiver that EMITS (`.call(`, `.set(`, `.write(`) and reads its own fields with tracked syntax (`(self.f)()`, `self.f.read()`, `self.f.cloned()`), flag every `use_effect` in the same file that calls a method of that name. Name-based and per-file, so it can over-flag; resolve by peeking, or by a reviewed `TRACKED_CALLEE_ALLOWED` entry. Proofs: a native test and a "several ranges in a row" Playwright spec.

Same lane, same file family: the input echo no longer closes the picker on the same frame; a double-click no longer clears the selection; focus returns to the trigger; the range closes at its end date; `close_on_select` (default true) and `close_delay` (default 300 ms) with a `keep_open` demo; `overlay` is forwarded; the unavailable-dates demo is relative to today (a double-opacity rule had hidden them); the multi-month panel width is fixed. The every-open fade was 144 px off-centre because the keyframes' `transform` replaced the anchor's own `transform` (class: `check-anchored-keyframes.sh`).

## 4. The listener inventory (rows 149 and 159)

**The class.** A listener added from `document::eval` (or a shipped or inline script) belongs to the PAGE, not to the Dioxus scope that evaluated it. Dropping the component drops the Rust task; the `addEventListener` registration stays on `window` or `document`, and a re-run adds another on top. For non-passive `wheel`/`touchmove` on `window` it also made every wheel tick wait for the main thread once any modal had opened (the cost row 149 found: Chromium `DidHandleInputEventSentToMain` 40/40 wheel ticks vs 0; wheel latency max 388 vs 143 ms with a busy main thread).

**Inventory (15 true leaks fixed).**

| Site | Leak |
|---|---|
| `scroll_lock.rs` | 4 listeners installed at the first lock and kept for the page |
| `pointer.rs` | 4 listeners on `window`, installed on first use |
| `form` fixture | 6 adds, 0 removes: 2 on `document`, and one more pair per visit |
| `focus-trap.js` | stacking registrations |
| `sidebar`, `theme.rs`, `index.html` | audited by the same scan |

**Construction.** `primitives/src/js_listener.rs` (`JsListeners` / `use_js_listeners`): the script registers through `listen(target, type, handler, options)`; removal is DERIVED (the value drops: unmount, effect re-run, lock release); `wheel`/`touch*` are passive unless the call says otherwise. The Popover modal arm uses the shared dialog driver.

**Gate.** `scripts/check-js-listeners.sh` fails every raw `addEventListener(` in `primitives/src` and `preview/src` (`*.rs`, `*.js`, `*.ts`) and `preview/index.html` that is not in `js_listener.rs`, has no `listener-ok: <reason>` marker, and is not a hand-paired registration in a `PAIRED_BY_HAND` file. `PAIRED_BY_HAND` is a ratchet that only shrinks; the audit counted 52 hand-paired sites in 11 files (row 167 migrates them). `check-blocking-scroll-listeners.sh` also sees `listen(.., { passive: false })`. Not covered, said plainly: another API (`web_sys`, `on*` properties, vendored scripts), the three Observers, and the generated `focus-trap.js` (its `.ts` source is scanned).

**Oracle.** `playwright/oracle/tier2-html/listener-inventory.spec.ts` asks Chromium itself (CDP `DOMDebugger.getEventListeners` on `window`, `document`, `<html>`, `<body>`; Playwright's own hit-target listeners are filtered by script source): (1) the multiset of (type, capture, passive) after opening and closing every modal, popover and menu consumer twice, and after entering and leaving the form and sidebar routes, equals the one taken BEFORE the first open (no warm-up cycle, so a lazily installed "for the session" listener fails); (2) no non-passive `wheel`/`mousewheel`/`touchstart`/`touchmove` remains; (3) scroll-lock timing (section 1); (4) no width shift under a forced classic scrollbar. Red proof was taken against the tree before the helper.

## 5. VirtualList and the shared virtualization pieces (row 143)

**Modes.** `virtualize: VirtualListMode::{Auto, ContentVisibility, Windowed}`; `Auto` (default) is `ContentVisibility` while `count <= auto_threshold` (default `DEFAULT_AUTO_THRESHOLD` = 1000), `Windowed` above. The row's plan said "default up to about 5k rows"; the threshold landed at 1000 because mounting every row is one main-thread task proportional to the count.

**Per scroll frame, main-thread ms** (release build, headless Chromium, 4-core VM; from `primitives/src/virtual/cv_chunks.rs`):

| Rows | one skippable element per row | one per 20 rows (chunked) | windowed |
|---|---|---|---|
| 1,000 | 7.7 | 1.1 | |
| 5,000 | 31 | 1.5 | 1.4 |

**First mount** (release, demo): about 90 ms for 1,000 rows; 205 ms for 5,000 (one 147 ms task). **Memory** (a 9-node row is about 4.5 KB): about 72 MB at 10k rows and 445 MB at 100k, against about 12 MB for a window. The survey's probe (Chromium 141, trust ratios): content-visibility is 3-5x faster to first layout and 2.5-3.5x lighter than rendering every row (10k rows +72 MB vs +194 MB).

**Why chunks.** `content-visibility: auto` makes the browser do per-frame work (an intersection check, then style/layout/paint bookkeeping) for every element it may skip, so one per row costs O(rows) per scroll frame. `primitives/src/virtual/cv_chunks.rs` groups `CHUNK_ROWS` = 20 consecutive rows into one skippable element, keyed by absolute position (`start + index`, so a prepend does not move rows between chunks); the price is up to 19 extra rows rendered around the viewport. The same module is used by `message_scroller`: its 2,000-row demo went from 20.3 to 3.7 ms per frame (the lane's debug numbers on a heavily loaded machine, transcript controller work included).

**Windowed engine.** `primitives/src/virtual/size_index.rs` is a Fenwick tree: measuring a row and finding the row at a pixel are O(log N) with no copy (the old engine rebuilt an O(N) `Vec` per measured row and cloned it per resize, about 24 MB per measurement at 1M rows). The scroll signal is quantized: the mounted range keeps hysteresis (re-centred once the viewport comes within `buffer / 2` rows of the edge), so a steady scroll re-renders about once per `buffer / 2` rows. Lane figures for 100k rows and a 1000 px scroll: 53 to 3 Rust renders, 275 to 48 ms. The spec asserts 1 to 6 renders for 1000 px and fewer than a third of the scroll events. Memory for a window stays flat from 10k to millions of rows; a single canvas is bounded by the browser's element-height cap (about 17M px in Firefox, 33M px in Chromium), roughly 300k rows of 100 px.

**Release-only assertions.** The per-frame thresholds (content-visibility 1000 rows under 4 ms per frame) run only when `PW_BUILD_PROFILE=release` (`buildProfile()` in `playwright/base-url.ts`), Chromium only (CDP `Performance.getMetrics`); a green debug run says nothing about them (CLAUDE.md, "Functional specs may run on debug SSG builds; timing specs only on release"). **Final-run status of these thresholds: appended by the main loop.**

**Not changed.** Find-in-page for the windowed mode above the threshold is row 153; the shared three-layer engine outline is row 154 (it can now reuse `virtual/cv_chunks.rs` and `virtual/size_index.rs`).

## 7. Variables versus layers for component composition (row 170)

**The problem.** Two rules from two sheets declare the same property on the same element at equal specificity; the later sheet wins, and sheet order is per route (and, before the bundle, per navigation). Instances so far: the Field label (14 px on the home gallery, 12.8 px on `/component/field/`; patching it with a specificity bump only moves the contest), and 208 of 2943 sheet pairs ordered both ways (section 2).

**Inventory.** `scripts/check-cross-component-overrides.sh` finds a NON-custom property declared in component X's stylesheet on an element that is really component Y's. Two kinds: `composed:<Y>` (X's class on Y's root, derived from the Rust: `FieldLabel` renders `<label class="dx-label dx-field-label">`) and `tag` (a bare `input|select|textarea|button|label` selector, the only way left to reach Y's root because `check-dx-class-prefix.sh` forbids naming another component's class). Baseline `scripts/check-cross-component-overrides.baseline.tsv`: **190 sites in 12 sheets** (149 composed, 41 tag), a shrink-only debt register.

| Sheet | Sites |
|---|---|
| sidebar | 65 |
| message_scroller | 25 |
| date_picker | 17 |
| button_group | 16 |
| toolbar | 16 |
| chart | 14 |
| input_group | 10 |
| command | 9 |
| form | 7 |
| data_table | 6 |
| field | 4 |
| item | 1 |

**Recommendation (decided in the lane, not yet owner-reviewed).**

1. **Slot variables for component-to-component composition.** The base reads `--dx-<component>-<property>` with its own default; the composer sets the VARIABLE on the base's element, never the property. A custom property is a different property from the one the base declares, so nothing contests anything: no specificity race, no order dependence (measured for Field to Label: identical in either sheet order). This is the CSS form of shadcn's `cn()`/tailwind-merge. Done: Label reads `--dx-label-{gap,color,font-size,font-weight,line-height}` (shadcn defaults; documented in label's "Slot variables"), Field sets `--dx-label-line-height: 1.375` and the invalid colour. Cost: a standalone Label changes from 12.8 px / 400 to 14 px / 500, which is shadcn's own. Four Field sites remain (horizontal-orientation `margin-top` on the label and on bare `button`/`input`/`select`). Burn-down order named by the lane: sidebar, message_scroller, date_picker, button_group, toolbar, input_group, chart, form; the small remainder is command, data_table, field and item.
2. **Later, an opt-in single `@layer dx` for the APP-override boundary** (so an app's unlayered CSS beats the library whatever the specificity or order). Prototype first, and diff with `scripts/compare-ssg-styles.mjs` (layered build against unlayered, expecting 0 differing routes) before anything ships. Layers do NOT replace step 1: inside one layer the same-property contest between two library sheets is unchanged.
3. **Explicitly NOT a `dx.compose` sub-layer.** A nested layer for composers would keep the same-property design and only decide the winner by a layer label that every composing rule has to be filed under by hand; it needs an `@layer` order statement ahead of both sheets on every route, which a copied-in component cannot guarantee; and it does not help the 41 `tag` sites (an element selector into another component's root).

**Risks to list before prototyping step 2 (analysis from the cascade-layer rules, not measured here):**

- **Resets.** Unlayered author CSS beats every layered rule regardless of specificity. An app or docs-site reset or element rule (`button { ... }`, `* { margin: 0 }`) would then beat library CLASS rules, where today a class outranks an element selector. `preview/assets/main.css` and any theme-level global rule need an explicit place in the layer order.
- **Tailwind v4.** Its preflight and utilities live in cascade layers (`theme`, `base`, `components`, `utilities`). The position of `dx` in the order decides the outcome and the library cannot know the app's layer names: declared after `utilities`, library rules beat `class="p-4"` on a dx element (the opposite of what a shadcn user expects); declared before `base`, preflight beats the library. The order statement must be documented and survive `dx components add` copies. Unlayered or Tailwind v3 apps simply beat the layer.
- **`!important` reverses layer order.** An `!important` declaration in the `dx` layer beats an `!important` in unlayered app CSS. The library carries some on purpose (the overlay-off `::backdrop` rule, the reduced-motion durations, the forced-colors outline), so each would become un-overridable by an unlayered app; list and review them before wrapping.
- **Delivery.** The bundle (`ssg-css-bundle.mjs`) concatenates sheets and rejects `@import`/`@charset`/`url()`; per-component sheets copied by `dx components add` would each need the wrapper or a shared order statement. Cascade layers are baseline in current engines (Chrome 99, Firefox 97, Safari 15.4).

**Overlap.** Row 145's state recipes (focus, invalid, disabled) are exactly the kind of rule a composer's sheet writes onto another component's root; build them as slot variables, not as more tag selectors, or the baseline grows. The gate refuses to grow (`--update-baseline` is shrink-only unless `--allow-grow` is given and justified in the commit).
