## 1. The a11y reference question

### 1.1 It exists. The backlog's framing needs correcting.

`dev-docs/component-backlog.md` row 73 says Carousel "needs an a11y
reference (no Radix primitive exists to build a conformance oracle
against)". Both halves of that parenthetical are true individually, but
together they imply no reference exists at all, and that's wrong for this
repo's own tier system:

- **Tier 1 (APG) exists, in full, at the pinned commit already checked out
  for this batch:** a local `w3c/aria-practices` checkout, `content/patterns/carousel/`
  (commit `7e4034b262bc0d25332e330d8a582aaf34113829`, same pin as
  `playwright/oracle/reference/7e4034b/`). It has a pattern page
  (`carousel-pattern.html`) and **two full worked examples** with their own
  CSS/JS/images — more complete than several patterns this repo has already
  vendored and shipped oracles against (e.g. the single-technique Table
  pattern).
- **Tier 3 (Radix) genuinely does not exist** — confirmed by grepping the
  actual clone, not by absence-of-memory: `find <local radix-ui/primitives checkout>/packages
  -iname "*carousel*"` returns nothing, and no `package.json` under
  `packages/` mentions "carousel" (radix-ui/primitives at `f7ecd5ab`,
  2026-07-31). That's fine: `dev-docs/conformance-harness.md`'s own tier
  table says Radix-parity is "opinion", useful "where the standards are
  silent" — here they aren't silent, so tier 3 simply doesn't apply, the
  same way it doesn't for the Table or Window Splitter patterns already in
  this repo's oracle suite.

So the correct framing is: **the standard (tier 1) reference is not
missing — it's just never been read.** What's actually missing is the
engine decision (Part 2).

### 1.2 The exact contract, read from the pattern page

`carousel-pattern.html` lines 114–185 ("WAI-ARIA Roles, States, and
Properties"), for the **basic** style (rotation + prev/next, no picker):

| Element | Role/attribute | Value |
|---|---|---|
| Carousel container | role | `region` (or `group` — "depends on the information architecture") |
| Carousel container | `aria-roledescription` | `carousel` |
| Carousel container | `aria-label` / `aria-labelledby` | author-supplied; **must not contain the word "carousel"** (redundant with the roledescription) |
| Rotation control | native `button` | accessible name toggles between e.g. "Stop ... rotation" / "Start ... rotation"; **no `aria-pressed`** — the changing label *is* the state |
| Each slide | role | `group` |
| Each slide | `aria-roledescription` | `slide` |
| Each slide | `aria-label` / `aria-labelledby` | unique if possible; otherwise **"N of M"** (explicitly called out as one of the only sanctioned uses of position/size text in an accessible name, because `group` doesn't support `aria-setsize`/`aria-posinset`) |
| Slides wrapper | `aria-live` (optional) | `off` while auto-rotating, `polite` when not |
| Slides wrapper | `aria-atomic` (optional) | `false` |

**Tabbed style** (slide picker = tabs): slide container becomes
`role="tabpanel"` "in lieu of `group`", "and it does not have the
`aria-roledescription` property" (pattern page's own words, line 157) —
picker is a `tablist` (`aria-label` e.g. "Choose slide to display"),
`tab` elements named "Slide N", implementing the Tabs pattern in full.

**Grouped style** (slide picker = plain buttons, one per slide, all in
page Tab order): picker buttons live in a `role="group"`, current slide's
button gets `aria-disabled="true"` (not native `disabled`, so it stays
Tab-reachable) — this repo's design sketch (§5) does not implement this
style; it's the "least keyboard-friendly" of the three per the pattern
page itself and shadcn doesn't have it either.

**Keyboard** (`carousel-pattern.html` lines 83–100, confirmed word-for-word
in both examples' own keyboard tables):
- If auto-rotate exists, focus entering the carousel stops it; it does not
  resume until the user explicitly reactivates the rotation control.
- `Tab`/`Shift+Tab`: ordinary tab order, no scripting required. Rotation
  control (if present) must be **first** in the carousel's tab sequence,
  before the slide content.
- Rotation control, Previous, Next: standard button semantics
  (`Enter`/`Space` activates); **activating them never moves focus**, so a
  user can hammer Next repeatedly.
- Tablist variant additionally gets the full Tabs pattern keyboard set
  (`ArrowLeft`/`ArrowRight` move focus **and** show the slide immediately —
  automatic activation — plus `Home`/`End`, roving tabindex). **Note: there
  is no Arrow-key row for the plain prev/next region itself** — the
  reference never binds arrow keys at the carousel-root level. Any
  root-level `ArrowLeft`/`ArrowRight` (which shadcn does add, see §1.4) is
  a Radix/shadcn-style addition, not an APG requirement.

### 1.3 Read the worked examples, not just the prose — they disagree with it

This is exactly the kind of thing "read the source, don't recite" is for.
Three concrete discrepancies between the pattern page's own prose and its
own worked examples (`examples/carousel-1-prev-next.html`,
`examples/carousel-2-tablist.html`, and their JS):

1. **The tabbed example's slide panels DO carry `aria-roledescription="slide"`**,
   contradicting the pattern page's explicit prose ("it does not have the
   `aria-roledescription` property"). Concrete markup, line 150 of
   `carousel-2-tablist.html`: `<div class="carousel-item" id="carousel-item-1"
   role="tabpanel" aria-roledescription="slide" aria-label="1 of 6">`. The
   example's own roles/properties table even defends this choice: "When
   combined with the `aria-roledescription`, a screen reader could announce
   a tab panel as a slide with its position." **Recommendation: follow the
   example (vendored, tested, calibration subject), not the abstract
   prose** — `role="tabpanel"` **and** `aria-roledescription="slide"`
   together.
2. **`aria-atomic` is inconsistent across three sources that all cite the
   same pattern.** The prose says `aria-atomic="false"` (optional). The
   actual vendored example sets **neither** `aria-live` nor `aria-atomic`
   as `atomic` — only `aria-live` toggles, no `aria-atomic` attribute
   appears anywhere in `carousel-1-prev-next.html` at all (checked by
   direct grep). Embla's own official accessibility plugin (§2.1) sets
   `aria-atomic="true"` unconditionally
   (`embla-carousel-accessibility/src/components/Accessibility.ts:262`) —
   the opposite of the prose. None of the three agree. **Recommendation:
   don't set `aria-atomic` at all in v1** (matches the actual tested
   reference, the weakest claim, easiest to revisit).
3. **The reference JS's own pause-on-hover/focus has a real quirk**, worth
   knowing before anyone assumes "vendored reference" means "bug-free":
   `examples/js/carousel-prev-next.js`'s rotation loop
   (`rotateSlides`, lines 178–192) advances the slide when
   `(!hasFocus && !hasHover && isPlayingEnabled) || hasUserActivatedPlay`.
   `hasUserActivatedPlay` latches `true` the first time a user clicks the
   rotation button to turn rotation **on**, and is never cleared except by
   clicking it back off — so **after a user has ever explicitly pressed
   play, hover/focus no longer pauses rotation**, which contradicts the
   pattern's own prose ("stops rotating whenever the mouse is hovering").
   This is very likely an oversight in the reference, not a deliberate
   design. **Recommendation: implement the prose's stated behavior (hover
   OR focus always pauses, unconditionally), and don't port this quirk** —
   when building an oracle rule from this, cite the prose, not this one
   corner of the example's own JS.
4. (Separately confirmed, not a discrepancy but worth flagging up front:)
   `hasReducedMotion = window.matchMedia('(prefers-reduced-motion:
   reduce)')`; if it matches, **`options.paused = true` is forced at init**
   — the reference disables autoplay outright for reduced-motion users, it
   doesn't merely drop a CSS transition (`carousel-prev-next.js:17-21`).
   Nothing in this repo's primitives currently reads
   `prefers-reduced-motion` at all (`grep -rl matchMedia
   primitives/src/*.rs` → no hits) — whichever engine option is chosen, an
   optional-autoplay feature is a **first** for this codebase on that axis
   too, and needs a `document::eval` read of `matchMedia(...).matches`
   regardless of which engine option below is picked, since Rust has no
   other way to observe it.

### 1.4 shadcn's own contract vs. APG's — the real gap table

Read in full: `apps/v4/registry/new-york-v4/ui/carousel.tsx` (local `shadcn-ui/ui` checkout)
(shadcn/ui `a87a63b2`, 2026-09-17). Confirmed it's the same file (modulo
import paths) across all three of shadcn's new "bases"
(`registry/bases/{radix,base,aria}/ui/carousel.tsx`) — **all three still
import `embla-carousel-react`**, which is itself the strongest possible
confirmation that none of Radix, Base UI, or React Aria has a carousel
primitive to build on; shadcn falls back to the same third-party engine
regardless of which headless foundation it's demonstrating.

| APG requirement | shadcn's `carousel.tsx` |
|---|---|
| `role="region"` + `aria-roledescription="carousel"` | Present (line 124-125) |
| Accessible name (`aria-label`/`labelledby`) on the region | **Absent** — not set anywhere in the component; left entirely to the caller, undocumented |
| `role="group"` + `aria-roledescription="slide"` on each item | Present (`CarouselItem`, line 161-162) |
| Slide accessible name / "N of M" | **Absent entirely** — no `aria-label` on `CarouselItem` at all |
| `aria-live` region (off while rotating / polite while not) | **Absent** — no live region anywhere; consistent with shadcn shipping no autoplay by default (that's a *plugin*, see §2.1) |
| Rotation control + label toggle | **Absent** — shadcn ships no autoplay/rotation UI; if you add `embla-carousel-autoplay` yourself you must build this button yourself too |
| Prev/Next buttons, accessible name | Present, via `sr-only` span text ("Previous slide"/"Next slide", lines 199/229) |
| Prev/Next don't move focus | Native `<button>` — true by default |
| Tab/Enter/Space semantics | Native `<button>` — true by default |
| Root-level `ArrowLeft`/`ArrowRight` | **Present but not an APG requirement** (`handleKeyDown`, lines 78-89) — Radix/shadcn-style addition |
| `prefers-reduced-motion` handling | **Absent** in the component; would depend entirely on which plugin (if any) the consumer adds |

So shadcn's Carousel is a thin, purely-visual wrapper: region + slide
*roles* are there, but the labeling, live-region, and rotation-control
half of the APG contract is left out completely, undocumented. Adopting
"shadcn's contract" verbatim, as this repo does structurally for every
other component, is **not** sufficient for APG conformance here — the gap
has to be closed by hand regardless of which engine option is picked. This
is baked into the design sketch (§5) as "APG additions on top of the
shadcn-shaped API".

### 1.5 RTL: a real, evidenced discrepancy worth flagging for the RTL lane

The brief asked me to check "embla and Radix-style components flip Arrow
keys in RTL" against source rather than repeat it. **Only half of that
holds up:**

- **Radix does, provably.** `packages/react/roving-focus/src/roving-focus-group.tsx`
  (radix-ui/primitives `f7ecd5ab`), lines 359-361:
  ```ts
  function getDirectionAwareKey(key: string, dir?: Direction) {
    if (dir !== Direction.RTL) return key;
    return key === 'ArrowLeft' ? 'ArrowRight' : key === 'ArrowRight' ? 'ArrowLeft' : key;
  }
  ```
  This is the shared primitive under `Tabs`, `RadioGroup`, `Menubar`, etc.
  — under `dir="rtl"` the physical key is **remapped before** being looked
  up in `MAP_KEY_TO_FOCUS_INTENT` (`ArrowLeft`→prev, `ArrowRight`→next).
  This repo's own `tabs.rs` (lines 319-335) has the un-flipped version
  today (`Key::ArrowLeft if horizontal => ctx.focus.focus_prev()`,
  unconditional) — exactly the gap the RTL-Rust lane in this batch is
  presumably closing.
- **shadcn's carousel does not**, and neither does embla at that layer.
  `carousel.tsx`'s `handleKeyDown` (quoted in §1.4) checks
  `event.key === "ArrowLeft"` unconditionally and always calls
  `scrollPrev()` — no `dir` branch anywhere in that function. RTL
  correctness instead comes from *inside* embla's engine:
  `embla-carousel/src/components/Axis.ts` (embla `85a5e3c`), `direction()`
  multiplies the translate offset by `sign = -1` for `rtl` horizontal
  (line 26, 46-48) — i.e. `scrollNext()` always means "logically next slide";
  RTL only flips the *sign of the pixel translation* used to render it, not
  which key calls which function.

**Why this matters for the design sketch:** we are not adopting embla
(see §2), so there's no engine-level sign flip to lean on for free. If our
own carousel adds root-level Arrow-key navigation (a shadcn/Radix-style
addition, not an APG one — see §1.2), it should follow **Radix's**
convention (swap the key→intent mapping under RTL), not shadcn's
(no swap, because embla is silently compensating underneath it) — that's
the only way it stays consistent with every other roving/orientable
primitive in this repo once `direction.rs` lands, and it's what a user
coming from `Tabs`/`RadioGroup` will expect. Concretely: `Carousel`'s own
keydown handler should consume the RTL lane's `direction.rs` the same way
`tabs.rs` will be updated to, and CSS scroll-snap actually makes the
*non*-keyboard part of this easier than embla's own approach — see §2.2's
RTL paragraph for why.

## 2. The engine question

### 2.1 What embla actually is (read from source, not the README)

Cloned `davidjerleke/embla-carousel` at `85a5e3cdb69756d6e139e697665cee72e1150e05`
(2026-09-12). Facts, not impressions:

- **Mechanism: manual `transform: translate3d(...)`, not native scrolling.**
  `packages/embla-carousel/src/components/Translate.ts` sets
  `node.style.transform` directly on every frame; there is no
  `scroll-snap-type` or native `scrollLeft` manipulation anywhere in the
  core engine. Embla is a full from-scratch reimplementation of
  drag/momentum/snap physics **on top of** absolute positioning, not a
  wrapper around the browser's own scroll-snap machinery. This is the
  single most important architectural fact for comparing options (a) and
  (b) below: porting embla's core is porting a physics engine, not a thin
  utility.
- **Size:** core engine (`packages/embla-carousel/src/components/`) is
  **3,155 lines across 39 TypeScript files** (`wc -l`, measured directly,
  recounted to be sure: `ls .../components/*.ts | wc -l` → 39).
  Largest files: `Engine.ts` (317, composition root), `EmblaCarousel.ts`
  (298, public API), `DragHandler.ts` (228, pointer/mouse drag +
  velocity), `EventHandler.ts` (144). Zero runtime dependencies
  (`npm view embla-carousel@8.6.0 dependencies` → empty). MIT licensed.
  **Version note:** the cloned git HEAD's own `package.json` says
  `9.0.0-rc03` (an in-flight, unreleased release candidate on `main`) —
  the actual published `npm view embla-carousel version` is **`8.6.0`**.
  Any real adoption would pin `8.6.0`, not this HEAD; the v9 API may still
  move before it ships.
- **Options confirmed from `Options.ts`:** `align` (`start`/`center`/`end`
  or a custom fn), `axis` (`x`/`y`), `direction` (`ltr`/`rtl`),
  `containScroll` (`trimSnaps`/`keepSnaps`/`false`), `slidesToScroll`
  (number or `'auto'`), `dragFree` (bool or `'snap'`), `dragThreshold`,
  `loop`, `skipSnaps`, `duration`, `startSnap`, `draggable`, `resize`,
  `focus`, `slideChanges`. `loop: true` is implemented via
  `SlideLooper.ts`/`ScrollLooper.ts` — cloning/repositioning edge slide
  nodes so the strip appears to wrap — real, non-trivial layout math, and
  a meaningful fraction of the engine's total LOC.
- **RTL is a first-class engine option** (`Axis.ts`, quoted in §1.5) — the
  translate sign flips, not the key bindings.
- **Accessibility is a *separate*, official plugin**
  (`embla-carousel-accessibility`), **not bundled in core**, and it
  explicitly cites the same APG page this report vendors:
  `Accessibility.ts`'s own header comment links
  `https://www.w3.org/WAI/ARIA/apg/patterns/carousel/examples/carousel-1-prev-next/`
  — independent, real-world corroboration that the APG page is the right
  reference to build against. It sets `role`/`aria-roledescription`/
  `aria-label` on the root and each slide, an "N of M" label generator,
  and a live region — but **sets `aria-atomic="true"` unconditionally**
  (line 262, contradicting the pattern prose, see §1.3).
- **Autoplay is also a separate plugin** (`embla-carousel-autoplay`), and —
  checked directly, not assumed — **it does not implement the
  focus-pauses-rotation requirement**. Its own event wiring
  (`Autoplay.ts` lines 111-118) only listens for `pointerdown`,
  `mouseenter`, `mouseleave` — no `focus`/`focusin` anywhere in the file.
  The accessibility plugin's own `focusin`/`focusout` handlers
  (`Accessibility.ts` lines 161-176) only update `lastFocusedSlide`
  bookkeeping for the live region's text, never call anything that stops
  autoplay. **Concretely: installing both official embla plugins together
  still does not satisfy APG's "stops rotating when keyboard focus enters
  the carousel" rule** — that wiring would have to be hand-written
  regardless of whether embla is adopted. This meaningfully changes the
  effort case for option (c): embla doesn't buy full APG conformance for
  free, only the drag/scroll physics.
- **The reference implementation itself doesn't scroll a strip at all.**
  Worth being explicit about, since it affects what the oracle can and
  can't assert: `carousel-prev-next.js`'s `showCarouselItem` (line
  149-160) toggles a `.active` CSS class on one `<div class="carousel-item">`
  at a time — a show/hide stack, not a scrolling/transform strip, and it
  has **no drag or touch-swipe support at all**. So the APG reference is
  authoritative for the **ARIA contract** (roles, labels, live region,
  keyboard) but not for the **visual mechanism** — neither embla's
  transform strip nor a CSS scroll-snap strip matches the reference's own
  implementation technique, and that's fine: the oracle rules below are
  written to assert role/attribute/keyboard behavior only, the same way
  `disclosure-navigation.spec.ts` and every other tier-1 spec in this repo
  already do, never DOM-shape.

### 2.2 Option (a) — CSS scroll-snap engine, written in Rust (recommended default)

Native `overflow-x: auto` (or `overflow-y`) + `scroll-snap-type: x
mandatory` on the track, `scroll-snap-align` on each `CarouselItem`,
`scrollTo({ left, behavior: 'smooth' })` via `document::eval` for
Previous/Next, selected index derived from an `IntersectionObserver`
(primary, safe) with `scrollend` as a progressive enhancement.

**Platform risk, checked live (WebSearch/WebFetch, not memory — this
sandbox's proxy does reach caniuse/MDN), since the brief specifically
asked whether there's a hard reason against this:**

| Feature | Status as of this check (2026-09-18) | Verdict |
|---|---|---|
| `scroll-snap-type` / `scroll-snap-align` | "Available across browsers since 2020... safe to use without fallbacks" (~95%+ global) | Safe to depend on directly |
| Smooth `scrollTo()` landing on the nearest snap point instead of the exact requested offset under `mandatory` snap | Real, documented browser behavior | **Not a risk here** — landing exactly on the snap point is the desired outcome for a carousel; this would only bite an unrelated same-page-anchor use case |
| `scrollend` event | Chrome since v114, Firefox since v109, **Safari only since v26.2** (caniuse, fetched live) — ~90% global today | Real but recent gap, not universal — see construction below |
| `scrollsnapchange` event (purpose-built "a new snap target was selected" signal) | MDN: "Limited availability — not Baseline" (fetched live, 2026-09-18) | Progressive enhancement only, never a dependency |
| `IntersectionObserver` | Baseline/universal for years | Safe to depend on directly — this is the primary mechanism, not `scrollend` |
| `prefers-reduced-motion` media query | Baseline/universal for years | Safe |

**Construction that follows from this data** (not "does it work", but
"what does the code have to do to not break on the ~10% of traffic
`scrollend` doesn't yet cover"): derive the selected index from an
`IntersectionObserver` on the slides (works everywhere, today); use
`scrollend` only to know *when to stop* sampling intersection ratios
during a smooth-scroll animation (a debounced `scroll` listener is the
fallback where `scrollend` is absent — same "feature-detect, degrade"
shape this repo already uses elsewhere, e.g. `top_layer.rs`'s
`visualViewport` handling). `scrollsnapchange` is worth wiring as a nicer
signal when present, but the design must not require it.

**What needs JS at all, precisely** (important because "zero JS" is not
quite true — being precise about *how little* is the actual selling
point): base scrolling (drag via touch/trackpad/wheel, keyboard Tab order)
is 100% CSS, zero JS, on every target including native/Blitz. Three
`document::eval` call sites are still needed, all short, all the existing
idiom (`primitives/src/pointer.rs`'s `document::eval(...).recv().await`
loop is the template): (1) init an `IntersectionObserver`/`scrollend`
listener and stream index-changed events back with `dioxus.send(...)`,
matching `pointer.rs`'s exact pattern; (2) `scrollTo({behavior:'smooth'})`
one-shot calls for Previous/Next/`scroll_to(index)`; (3) a single
`matchMedia('(prefers-reduced-motion: reduce)').matches` read, only if the
optional autoplay feature is used. On native/Blitz (`not(feature =
"web")`), all three no-op exactly the way every other `document::eval`
call in this crate already no-ops there today (confirmed pattern:
`primitives/src/lib.rs`'s `focus_trap_script`, `top_layer.rs`'s
`use_popover_sync`) — CSS scroll-snap markup still renders on native, so
worst case there is "buttons don't animate" on a target this repo doesn't
build in CI anyway (`grep -rl native .github/workflows/` → nothing;
confirmed already true of every overlay primitive, not a new gap this
introduces).

**RTL is easier here than under embla**, not harder: because DOM order of
`CarouselItem`s never changes, "the next slide" is always "the next
sibling", and scrolling an element into view (`scrollIntoView`/its
computed offset) is direction-agnostic — the browser's own RTL layout
already puts it at the correct physical position. There's no
sign-flip-the-translate step to get right at all (contrast embla's
`Axis.direction()`, §2.1). The only RTL work left is the **keyboard**
question from §1.5 (swap which physical arrow key means "prev"/"next"),
which is a `direction.rs`-consuming one-line change in the keydown match,
identical in shape to what `tabs.rs` needs.

**`loop` is the one place this option is genuinely harder than doing
nothing**: true infinite-loop scroll-snap (wrapping past the last slide
back to the first without a visible jump) needs either duplicated
edge-clone slides (what embla does, `SlideLooper.ts`) or a
detect-the-edge-and-silently-`scrollTo`-without-`smooth`-behavior jump.
Recommend **deferring `loop` to a fast-follow** (ship `can_scroll_prev` /
`can_scroll_next` going `false`/disabled at the ends in v1, exactly like
dignifiedquire's and shadcn's own default behavior) — this is a real
scoping lever for the effort estimate in §6, not a hidden gap: neither
shadcn's own default demo nor dignifiedquire's port implements loop
either, so shipping without it in v1 is shipping at parity with both
existing references, not behind them.

### 2.3 Option (b) — port embla's core engine to Rust

Considered and **not recommended**. Sizing it honestly: 3,155 lines of
TypeScript, but that count understates the real cost — it's a from-scratch
drag/velocity/spring/resize/loop physics engine (§2.1), not a set of pure
functions. A faithful port needs: pointer capture + velocity sampling
(`DragHandler.ts`/`DragTracker.ts`), a spring-based settle animation
(`ScrollBody.ts`/`ScrollAnimator.ts`, frame-loop driven), resize/reinit
handling (`ResizeHandler.ts`), and the loop-via-clone-nodes math
(`SlideLooper.ts`/`ScrollLooper.ts`/`ScrollContain.ts`) — none of which
have a Rust-side equivalent anywhere in this repo to build on (the closest
prior art, `primitives/src/pointer.rs`, is 204 lines and only tracks
current position, no velocity/momentum). Realistically this is a multi-week,
high-defect-risk rewrite of physics code that the CSS scroll-snap option
gets from the browser for free, in exchange for pixel-identical parity
with embla's specific drag feel — a property nothing in this repo's own
`recommended-implementations.md` culture ("prefer platform features;
fall back to JavaScript only where no platform feature exists" — literally
the dialog/`<dialog>` finding that reshaped this repo's overlay
architecture) would ask for. Listed for completeness per the brief; not
carried into the comparison table as a live contender.

### 2.4 Option (c) — JS interop: embla bundled as an asset, `document::eval` bridge

**Correction to the brief's own framing, found by reading the actual
crate, not assumed:** this would **not** be "the first JS dependency of
any component here." This repo already ships one JS asset today —
`primitives/src/js/focus-trap.js`, hand-authored TypeScript at
`primitives/src/ts/focus-trap.ts` (106 lines), compiled by
`primitives/build.rs`'s `lazy_js_bundle` step and loaded via `asset!` +
`document::Script` (`primitives/src/lib.rs` lines 76-118). What's actually
true, precisely:
- It's used **only on the native/Blitz arm** (`#[cfg(not(feature =
  "web"))]`, `lib.rs:89`) — every `feature = "web"` build (the wasm
  client **and** the fullstack SSG server) never references it at all.
  So embla would be this repo's **first JS asset shipped to the web
  arm specifically** — a real first, just not the one stated.
- It's **first-party TypeScript authored in this repo**, not an external
  npm package. Embla would be this repo's **first third-party npm runtime
  dependency**, full stop — that framing survives the correction and is
  the actually load-bearing one.

**The packaging gap is concrete, not speculative** — checked every shipped
component's manifest, not just one: every `preview/src/components/*/component.json`
(62 files, counted directly with `find ... -iname component.json | wc -l`,
then `grep`'d exhaustively for every top-level key across all of them)
uses only seven possible keys —
`name`, `description`, `authors`, `exclude`, `cargoDependencies`,
`componentDependencies`, `globalAssets`. **None has ever declared an npm
package.** `cargoDependencies` covers `dioxus-primitives` itself (a git
dependency) plus small crates like `dioxus-icons`; `globalAssets` covers
the shared theme CSS. There is no field for "also run `npm install X`",
and `preview/package.json` itself (the showcase app) only has `stylelint`
and its config packages as dependencies — zero runtime/browser-facing npm
packages anywhere in this repo today, in the library or the consumer-facing
manifest. A `dx components add carousel` today copies Rust + CSS files and
expects `cargo` to resolve the rest; there's no CLI-side step that would
`npm install embla-carousel` into the consumer's project the way shadcn's
own CLI does. Making this work means **either** extending the
`component.json` schema (a tooling change with no precedent, affecting the
`dx components add` machinery itself, out of scope for a single
component) **or** vendoring embla's built bundle as an `asset!` the same
way `focus-trap.js` is vendored (feasible mechanically — `lazy-js-bundle`
already exists as a build-dependency — but now the *consumer's* copy of
`carousel.rs` references an `asset!` pointing at a file that only exists
inside `dioxus-primitives`'s own crate, not something `dx components add`
copies into their project at all, so the maintenance/update story is
opaque to a consumer who "owns their copy" the way this repo's whole
`dx components add` pitch promises for every other component).
- SSG/hydration: embla measures the DOM (`getBoundingClientRect` on every
  slide) to compute snap points — meaningless during a fullstack SSG
  prerender (a host binary, no real layout), so it would need the same
  `feature = "web"`-gated pattern this repo's overlays already use
  (`scripts/check-cfg-axis.sh`'s enforced rule), engine-initialized
  client-side only, with a plain, unstyled-but-correct server-rendered
  fallback markup (this part is genuinely no harder than what
  `top_layer.rs` already does).
- **It still doesn't buy full APG conformance for free** — §2.1's
  autoplay-plugin finding (no focus-pause even with both official plugins
  installed) means the same hand-written ARIA/live-region/focus-pause
  layer from §5 is needed on top of embla regardless.
- **Coordination note, not a blocker:** the concurrent Chart lane
  (same batch) is evaluating its own third-party-library question for
  `recharts`; its scratch work as of this writing
  (in the Chart lane's own scratch directory) is experimenting with
  `plotters` (a pure-Rust/wasm canvas charting crate, not an npm package)
  rather than adopting `recharts` — if that holds, Carousel's embla path
  would in fact be this repo's first true npm dependency; if Chart lands
  on `recharts` first, that lane gets there first instead. Worth knowing
  before treating "first npm dependency" as a Carousel-specific
  precedent-setting cost — it's a repo-wide threshold either lane could
  cross first, and it's each lane's own decision to make on its own
  merits, not a queue position.

Not recommended as the default, for the reasons above, but it is the
only option that gets embla's actual drag feel, `containScroll`, and
`dragFree` — genuinely viable if the user's priority is matching
shadcn's demo pixel-for-pixel over this repo's zero-JS-so-far posture.

### 2.5 Option (d) — adopt `dignifiedquire`'s `carousel.rs`

Read in full, both layers, not summarized from the backlog's one-line
note. `dignifiedquire/dx-components` cloned at `5af3cc292559a0e8d73c7b9a827c4ca08ef34d99`
(2026-08-21, matches `dev-docs/backlog.md` row 35's citation exactly),
dual MIT/Apache-2.0 (confirmed: `LICENSE-APACHE`/`LICENSE-MIT` at repo
root, same as this repo). **Re-verifying the backlog's "no adoptable
code" judgement — it holds, precisely because of what the code actually
does:**

- `primitives/src/carousel.rs` (412 lines) is **index-only state**: a
  `usize` current index, a `slides_per_view: usize` prop the doc comment
  admits "stands in for the DOM measurement embla performs in shadcn's
  source" — i.e. it doesn't measure the DOM at all, and boundary/step
  math silently goes wrong the moment a caller's CSS breakpoints (e.g. a
  responsive `basis-1/2` → `basis-1/3`) drift out of sync with this
  number. There is no scroll-snap, no transform, no drag, no touch, no
  live region, no rotation control, no autoplay, no RTL handling.
- `components/src/carousel.rs` (289 lines, the styled layer) supplies the
  only actual movement: `format!("transform: translateX({offset}%);")`
  driven by the same index (line 129) with a Tailwind
  `transition-transform duration-300`. It is `role="region"` unconditionally
  with **no accessible-name requirement surfaced anywhere in the API** —
  the primitive never sets or requires `aria-label`; a caller *could*
  smuggle one in via the `attributes` spread, but nothing in the API
  documents or enforces it.
- Keyboard: `ArrowLeft`/`ArrowRight` (or Up/Down vertical) bound directly
  on the root's `onkeydown` (`primitives/src/carousel.rs` lines 203-225) —
  a real, working root-level Arrow-key handler (matching shadcn's own
  addition, §1.4), also with no RTL swap.
- **What *is* worth reusing, explicitly, despite the code not being
  adoptable:** the *shape*. `CarouselApi` (a plain read-only snapshot
  struct: `current_index`, `total_slides`, `can_scroll_prev/next`) mirrors
  shadcn's `setApi`/`CarouselApi` surface almost exactly, and
  `use_carousel()` as the context-accessor name is exactly what the
  brief's own suggested API asks for. The design sketch in §5 keeps these
  names for ecosystem consistency (a Dioxus developer who's seen either
  this repo's other primitives or `dx-components`' carousel should
  recognize the shape immediately) while replacing the entire index/
  transform mechanism underneath with CSS scroll-snap (§2.2). "No
  adoptable code" is correct about the *implementation*; the naming
  convention is worth keeping anyway.
- `dx-components` does have its own Playwright coverage
  (`playwright/carousel.spec.ts`, 210 lines) and Rust unit tests
  (`primitives/tests/carousel.rs`, 233 lines) — not read in depth, since
  the architectural verdict above doesn't depend on their contents, but
  worth knowing they exist if anyone later wants to see what that fork
  considered worth testing for an index-only carousel.

## 4. Recommendation

**Option (a): a CSS scroll-snap engine in `primitives/src/carousel.rs`,
calibrated against both vendored APG example pages.** The brief's stated
prior holds up under the evidence gathered, and none of the three named
risks turned out to be a hard blocker:

- `scroll-snap-type` itself: safe, 95%+ since 2020.
- Smooth-scroll + snap interplay: the one documented quirk (lands on the
  nearest snap point) is the *desired* behavior for a carousel, not a bug
  to work around.
- `scrollend`: real but recent gap (Safari only since v26.2), mitigated by
  making `IntersectionObserver` — universal — the primary selected-index
  signal and treating `scrollend`/`scrollsnapchange` as pure progressive
  enhancement, never a dependency.

It's also the only option that is simultaneously: zero new dependencies
(Cargo or npm), consistent with this repo's stated platform-features-first
architecture (`recommended-implementations.md`'s `<dialog>` finding),
compatible with the existing `dx components add` packaging model with no
schema changes, and RTL-favorable by construction rather than by
sign-flip bookkeeping (§2.2).

**Option (c) is the real alternative** if the user's priority is "match
shadcn's own demo exactly, including mouse-drag feel and `loop`", accepts
this repo's first npm dependency, and is willing to treat the
`component.json`/`dx components add` gap as follow-up tooling work rather
than a blocker. It is not recommended as the default only because that
combination of costs is larger than the CSS engine's, not because it's
unworkable.

**Option (b) is not a live contender** — sized honestly in §2.3, it's a
physics-engine port with no prior art in this repo, for a payoff (drag
feel parity) that (a) already gets close enough to via native scrolling
and (c) gets exactly, at far lower engineering risk than reimplementing it.

**Option (d) is not a live contender either** — re-verified, not just
repeated from the backlog: it would need nearly all of (a)'s APG-contract
work added on top of it anyway (§2.5), while contributing no scroll
mechanism worth keeping.

## 5. Design sketch (assumes option (a); adjust the interop layer only if the user picks (c))

### 5.1 Primitive API (`primitives/src/carousel.rs`)

Mirrors shadcn's component names (familiar to anyone who's used the
reference implementation) and dignifiedquire's `CarouselApi`/`use_carousel`
naming (§2.5), but **flattens props** rather than taking an opaque `opts`
bag — matching this repo's own convention in every primitive read for this
report (`tabs.rs`'s flat `default_value`/`value`/`on_value_change`,
`resizable.rs`'s flat `direction` field), not shadcn's single
`opts: CarouselOptions` object:

```rust
pub enum CarouselOrientation { Horizontal, Vertical }     // matches resizable.rs's ResizableDirection shape
pub enum CarouselAlign { Start, Center, End }              // -> scroll-snap-align

pub struct CarouselProps {
    pub orientation: ReadSignal<CarouselOrientation>,      // default Horizontal
    pub align: ReadSignal<CarouselAlign>,                  // default Start (shadcn/embla default Center; Start reads better for peek-next layouts -- open question, not load-bearing)
    #[props(default)] pub r#loop: ReadSignal<bool>,        // v1: accepted but not implemented -- can_scroll_prev/next simply stay false at the ends; see 2.2
    #[props(default)] pub on_select: Callback<usize>,      // fires on every settled index change (embla's api.on('select', ...) equivalent)
    pub attributes: Vec<Attribute>,
    pub children: Element,
}

pub struct CarouselApi { pub selected: usize, pub count: usize, pub can_scroll_prev: bool, pub can_scroll_next: bool }
pub fn use_carousel() -> CarouselApi                        // read-only snapshot, dignifiedquire-shaped
// plus, on the context, imperative actions a caller can reach without a full re-render subscription:
//   scroll_to(index: usize), scroll_prev(), scroll_next()

pub fn Carousel(props: CarouselProps) -> Element            // role="region", aria-roledescription="carousel"; PANICS-IN-DEBUG or a tracing::warn! if neither aria_label nor aria_labelledby is supplied via attributes -- closing shadcn's own undocumented gap (1.4) by construction, the same way this repo already treats other required-label components
pub fn CarouselContent(props) -> Element                    // the scroll-snap track: overflow-{x,y}: auto; scroll-snap-type; data-orientation, mirroring resizable.rs's own data-orientation convention
pub fn CarouselItem(props) -> Element                       // role="group", aria-roledescription="slide", scroll-snap-align; default aria-label "{index+1} of {count}" unless the caller overrides it (APG's sanctioned fallback, 1.2) -- needs each item to know its own index + sibling count, via the same collection-registration idiom `tabs.rs`/`select` already use, not a hand-rolled counter
pub fn CarouselPrevious(props) -> Element                   // native <button>, disabled when !can_scroll_prev, aria-label default "Previous slide"
pub fn CarouselNext(props) -> Element                       // symmetric
```

### 5.2 APG additions on top of the shadcn shape (closing §1.4's gap)

- `Carousel`'s region gets a **required** accessible name (see above) —
  the one piece of the contract shadcn itself silently skips.
- `CarouselItem`'s "N of M" default label, generated from the same
  collection/index machinery `Tabs`/`Select` already use to know "am I
  item 3 of 7" — not a new counting mechanism.
- **Optional** rotation control + live region, only when the caller opts
  into autoplay (a `CarouselAutoplay` prop/component, not forced onto
  every consumer who just wants a manually-paged carousel — matches
  shadcn's own "autoplay is opt-in" posture, but actually implements the
  contract instead of leaving it undocumented):
  - `aria-live` on the content wrapper: `"off"` while auto-rotating,
    `"polite"` once stopped (§1.2/1.3 — no `aria-atomic`, matching the
    tested reference, not the prose).
  - A rotation-control button, first in tab order (before
    `CarouselContent`), label toggling "Start automatic slide show" /
    "Stop automatic slide show" (§1.2's exact reference wording), no
    `aria-pressed`.
  - Focus entering the carousel **or** hover **always** pauses rotation,
    with no latch that re-enables it afterwards (§1.3 point 3 — the one
    place this sketch deliberately does not copy the reference's own JS).
  - `prefers-reduced-motion: reduce` forces autoplay off at mount,
    unconditionally (§1.3 point 4) — the one required `document::eval`
    read even under option (a)'s "almost no JS" framing.

### 5.3 Keyboard rows (final, reconciling §1.2 and §1.5)

| Key | Where | Behavior |
|---|---|---|
| `Tab`/`Shift+Tab` | anywhere | Ordinary tab order; rotation control (if present), then Previous, then Next, then slide content — matches both vendored examples exactly |
| `Enter`/`Space` | rotation control | Toggle autoplay |
| `Enter`/`Space` | Previous/Next | Move one slide; **never moves focus** (native `<button>` gives this for free) |
| `ArrowLeft`/`ArrowRight` (horizontal) or `ArrowUp`/`ArrowDown` (vertical) | `Carousel` root, when focus is inside it | **Not an APG requirement** (§1.2) — a shadcn/Radix-style addition, kept for parity with shadcn's own demo. Must consume `direction.rs` and swap Left/Right under `rtl`, **Radix's convention** (§1.5), not shadcn's own un-swapped one |
| `ArrowLeft`/`ArrowRight`/`Home`/`End` | tablist variant's tabs (§5.4) | Full Tabs pattern automatic-activation model — inherited free from `Tabs`, already RTL-correct the moment the RTL-Rust lane updates `tabs.rs` |

### 5.4 Tablist variant

The APG tabbed style (§1.2) is close enough to this repo's existing
`Tabs`/`TabList`/`TabTrigger` roving-tabindex machinery
(`primitives/src/tabs.rs` lines 280-340: `ArrowLeft`/`ArrowRight`/`Home`/`End`,
roving `tabindex`, automatic activation on focus) that it should be
**composed**, not reimplemented: a `CarouselTabList`/`CarouselTab` pair
that is a thin wrapper delegating focus/roving-tabindex to the same
`use_collection_provider` pattern `Tabs` already uses, differing only in
rendering `aria-roledescription="slide"` on the panel (§1.3 point 1 — the
tested example's own choice, not the prose's) alongside `role="tabpanel"`.
This is the single biggest scope-reduction opportunity in the whole
design: it turns "reimplement the Tabs keyboard pattern" into
"reuse it", and picks up the RTL fix for free the moment `tabs.rs` gets
one.

### 5.5 `style.css` (shape only — full CSS is implementation, not a research artifact)

Translates shadcn's Tailwind utility classes (`carousel.tsx`, §1.4) into
this repo's plain `dx-`-prefixed classes, per the row-32 construction
(`scripts/check-dx-class-prefix.sh`): `.dx-carousel`, `.dx-carousel-content`
(the `overflow: hidden` **outer** wrapper — shadcn's own two-layer
structure, an outer clipping div plus an inner flex track, translates
directly to "outer: `overflow: hidden`" / "inner: the actual
`overflow-{x,y}: auto; scroll-snap-type` element" for the CSS-scroll-snap
engine), `.dx-carousel-item` (`scroll-snap-align`, `flex-shrink: 0`,
sizing left to the caller via Tailwind-style `basis` utilities or plain
width/percentage, same as shadcn), `.dx-carousel-previous`/`-next`
(absolute-positioned circular buttons, shadcn's own `top-1/2 -left-12`
positions translated to logical (`inset-inline-start`) properties per
this batch's RTL-CSS lane's own remit — **note for that lane**: this is
exactly the class of rule `check-css-logical-properties.sh` should be
catching once Carousel exists), orientation via `[data-orientation="vertical"]`
attribute selectors matching `resizable.rs`'s own convention.

### 5.6 Demo(s)

One `preview/src/components/carousel/variants/main/mod.rs`, matching the
one-file-multiple-blocks shape already used by every other component's
`variants/main/` (confirmed structurally — `resizable`/`tabs` both have
exactly one `variants/main/mod.rs`, no per-demo directories): a basic
multi-slide demo (images or cards, matching shadcn's own default demo),
an "N slides per view" demo (`basis-1/2`/`basis-1/3` equivalent), a
vertical-orientation demo, and a tablist-variant demo (§5.4). Autoplay
demo optional/secondary, given it's the one part of the contract with
real behavior to get right (§5.2) rather than pure layout.

### 5.7 Oracle plan

New `playwright/oracle/tier1-apg/carousel.spec.ts`, structured exactly
like `disclosure-navigation.spec.ts` (read in full for this report,
`playwright/oracle/tier1-apg/disclosure-navigation.spec.ts` lines 1-90):
a header doc block quoting the exact pattern-page/example prose this
report already extracted (§1.2), each rule cited to its source line, two
`test.describe` blocks — **"Reference: W3C's own Carousel example"**
(loaded via `pathToFileURL` against the newly-vendored
`playwright/oracle/reference/7e4034b/content/patterns/carousel/examples/
carousel-1-prev-next.html`, §1.6) and **"Library: our own `carousel`"**
(against `http://127.0.0.1:8080/component/?name=carousel&`) — running the
identical rule set against both subjects, dual-subject exactly like that
file and `focus-restore-reference.spec.ts` before it. A second spec (or a
second `describe` block in the same file, following whichever of those
two precedents the reviewing lane prefers) does the same against
`carousel-2-tablist.html` for the tablist variant (§5.4), reusing
`keyboard-matrix.spec.ts`'s existing Tabs-pattern rows rather than
re-deriving them, since §5.4 composes the real `Tabs` machinery.

Rules to encode (each cited to §1.2/§1.3's exact source lines, the way
this report already has them):
1. Region role + `aria-roledescription="carousel"` + non-empty accessible
   name not containing the word "carousel".
2. Each slide: `role="group"` + `aria-roledescription="slide"` +
   accessible name (unique or "N of M").
3. Prev/Next: native button, accessible name, `disabled`/`aria-disabled`
   only at the loop-off boundary (since §2.2 defers `loop`), activating
   never moves focus.
4. Tab order: rotation control (if present) first, then Prev/Next, then
   slide content — never the reverse.
5. Rotation control (autoplay variant only): label toggles between the
   two exact reference strings; no `aria-pressed`; `Enter`/`Space` toggles.
6. Live region (autoplay variant only): `aria-live="off"` while rotating,
   `"polite"` once stopped; focus-in or mouseover always stops it, with no
   exception (deliberately **not** porting the reference JS's own
   `hasUserActivatedPlay` latch bug, §1.3 point 3 — this rule should be
   cited to the *pattern page's prose*, not the example's own script, and
   is expected to be one of the rare cases where this repo's own rule is
   *stricter* than the literal reference implementation).
7. `prefers-reduced-motion: reduce` ⇒ autoplay never starts (§1.3 point 4).
8. Tablist variant: `role="tablist"`/`tab`/`tabpanel`, roving tabindex,
   `aria-selected`, automatic activation on Arrow/Home/End — largely a
   thinner wrapper around `keyboard-matrix.spec.ts`'s existing Tabs rows
   per §5.4, run against the panel's additional `aria-roledescription="slide"`
   (§1.3 point 1) as a Carousel-specific addition.
9. axe scan, closed and (autoplay variant) open, per the two-state
   convention `conformance-harness.md`'s axe section already establishes.

## 8. Decisions needed from the user

1. **Engine: (a) CSS scroll-snap in Rust, or (c) embla via JS interop?**
   **Default: (a)** — matches this repo's stated platform-first
   architecture, zero new dependencies, no `dx components add` tooling
   change, RTL-favorable by construction. Pick (c) only if pixel-parity
   with shadcn's own drag feel and `loop`/`dragFree` matter more than
   those costs.
2. **If (a): ship `loop` in v1, or defer it?** **Default: defer** —
   neither shadcn's nor dignifiedquire's own default carousel has it
   either, and it's the single largest scope lever in §6's estimate.
3. **Autoplay/rotation-control: in v1, or a fast-follow?** **Default:
   fast-follow** — a manually-paged carousel is fully APG-conformant on
   its own (§1.2's basic style has no rotation requirement at all); the
   live-region/focus-pause work in §5.2 is real but separable.
4. **Root-level `ArrowLeft`/`ArrowRight` on the plain (non-tablist)
   variant: include, as shadcn/Radix-style parity, or omit as
   non-APG-required?** **Default: include**, RTL-swapped per Radix's
   convention (§1.5/§5.3), since it's low-cost once `CarouselContent`
   exists and users coming from shadcn will expect it.
5. **Tablist variant: ship alongside the basic variant in v1, or
   fast-follow once §5.4's `Tabs`-composition is proven out on the basic
   variant first?** **Default: fast-follow by one iteration** — it's
   cheap (§5.4) but is still a second full variant with its own oracle
   pass; sequencing it after the basic variant is stable de-risks both.
6. **Sequencing against the RTL-Rust lane**: Carousel's own RTL keyboard
   correctness (§5.3) is a one-line change once `primitives/src/direction.rs`
   exists, but has nothing to consume until it does. **Default:** land
   Carousel's LTR behavior first (it's correct and complete on its own),
   file the RTL swap as a follow-up once `direction.rs` merges, the same
   way `tabs.rs` itself will need to.
