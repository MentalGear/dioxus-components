# Chart component — research report (lane B3-R1, batch 3)

**Date:** 2026-09-19
**Status:** awaiting the user's decision — options and defaults in §8

Research only, no repo edits. Base: `cbae695`. Every claim below is cited to a file
path + commit SHA (cloned this session, not recited from memory) or to a command
this session actually ran. Where something is architecture-based rather than
build-verified, it says so.

## TL;DR

**Build a new, in-repo, pure-RSX SVG chart engine** (`primitives/src/chart/`), styled
exactly like every other primitive in this repo. Port shadcn's *conceptual* layer
faithfully — `ChartConfig` → `--color-<key>` CSS variables, a `ChartContainer` with
`data-chart="<id>"`, `ChartTooltip`/`ChartLegend` — but **not** its literal
children-composition API, which is React-specific and has no Dioxus equivalent
(§1.4). No new Cargo dependency. This is the only option that satisfies this repo's
hard constraints (hydration parity, real-DOM a11y, wasm32+Blitz, no JS bundle) *by
construction* rather than by careful discipline on top of a mismatched tool. Full
comparison in §3–5; decision points for you in §8.

## 1. shadcn's Chart layer — read from source, not from memory

Cloned `shadcn-ui/ui` to a local scratch checkout, commit `a87a63b2ca25143d26c8bd0903e4e9bc77b3f824`
(2026-09-17, MIT — that checkout's `LICENSE.md`). The whole layer is one file:
`apps/v4/registry/new-york-v4/ui/chart.tsx` (374 lines, read in full).

### 1.1 What it provides, exactly

| Export | What it does | Recharts APIs it leans on |
|---|---|---|
| `ChartConfig` | `Record<key, { label?, icon?, color? \| theme? }>` — a plain data type, nothing rendered | none |
| `ChartContainer` | Generates a `chart-<id>` string, provides `ChartConfig` via context, renders `<div data-chart={id}>` wrapping `<ChartStyle>` + `<RechartsPrimitive.ResponsiveContainer>{children}</ResponsiveContainer>` | `ResponsiveContainer` (measures the div, injects `width`/`height` into its single child) |
| `ChartStyle` | Emits a literal `<style>` tag: for each configured key with a `color`/`theme`, writes `[data-chart=<id>] { --color-<key>: <value>; }`, once per theme selector (`""` for light, `".dark"` for dark) | none — pure string templating |
| `ChartTooltip` | `= RechartsPrimitive.Tooltip` (a bare re-export) | `Tooltip` |
| `ChartTooltipContent` | Reads `active`/`payload` from Recharts' tooltip render-prop; looks up each payload item's config by `dataKey`/`name` via `getPayloadConfigFromPayload`; renders a label + one row per series (swatch color from `item.payload.fill ?? item.color`, i.e. **read back from Recharts' own computed render data**, not from `ChartConfig` directly) | Recharts' tooltip payload shape (`payload[].dataKey/name/value/color/payload.fill`) |
| `ChartLegend` | `= RechartsPrimitive.Legend` (bare re-export) | `Legend` |
| `ChartLegendContent` | Same payload-lookup idiom as the tooltip, renders a swatch + label per legend entry | Recharts' legend payload shape |

`ChartContainer`'s own class list hard-codes CSS overrides onto Recharts'
internal class names (`.recharts-cartesian-axis-tick_text`, `.recharts-dot`,
`.recharts-sector`, etc., line 67) — i.e. **shadcn's styling reaches directly into
Recharts' generated DOM structure**, not just its own wrapper markup. That
coupling cannot be ported at all (a Rust engine will never produce
`.recharts-*` classes), which is fine — it just means "port the concept," not
"port the file."

Every demo passes `accessibilityLayer` on the top-level chart component
(`<BarChart accessibilityLayer data={...}>`, confirmed in
`charts/chart-bar-default.tsx`, `chart-area-default.tsx`,
`chart-bar-interactive.tsx` — all read in full) and `cursor={false}` on
`ChartTooltip` (Recharts' default hover-rectangle/line cursor is turned off
in favor of the bar/line's own hover state). `RadarChart`/`PieChart`/
`RadialBarChart` demos never pass `accessibilityLayer` — Recharts only wires
it into the Cartesian-chart family (`src/chart/CartesianChart.tsx:18,75`,
confirmed below), not the polar family, so shadcn simply doesn't ask for it there.

| Bar | 10 | default, horizontal, stacked, negative, mixed, label(+custom), multiple, active, interactive |
| Line | 10 | default, dots(+colors/custom), step, linear, label(+custom), multiple, interactive |

### 1.3 The accessible-name / description convention

`ChartContainer` sets no `role`/`aria-label` of its own anywhere in `chart.tsx` —
accessibility for the SVG root is entirely Recharts' `accessibilityLayer`
responsibility (§2), not shadcn's. shadcn's own contribution is purely visual/
theming.

### 1.4 The finding that matters most: this is not portable as one API

Recharts' composition model is **children-as-configuration**: `<BarChart
accessibilityLayer data={chartData}><CartesianGrid/><XAxis dataKey="month"/>
<ChartTooltip .../><Bar dataKey="desktop" fill="var(--color-desktop)"/></BarChart>`
works because `BarChart` walks `React.Children` (and internally,
`react-redux` state built from what those children declare) to assemble one
shared scale/layout from sibling elements' *props*, before ever rendering
anything. `ChartContainer` itself is complicit: its `children` type is
literally `React.ComponentProps<typeof ResponsiveContainer>["children"]`
(chart.tsx line 50) — it is explicitly typed as "whatever Recharts' own
`ResponsiveContainer` accepts," not an arbitrary Dioxus-style `Element`.

Dioxus's `Element` gives a parent no equivalent of `React.Children.map`/
`cloneElement`: by the time a Dioxus component receives `children: Element`,
it is an opaque rendered tree, not an introspectable list of
(component-type, props) pairs. **No Rust chart crate changes this** — it is a
property of the two UI frameworks' composition models, not of whichever
engine draws the marks. Concretely, this means a faithful port cannot offer
`Chart { XAxis {...} Bar { dataKey: "desktop" } }` and have `Chart`
reconfigure itself from what got nested inside it. The single Dioxus-native
chart crate that exists (`dioxus-charts`, §4b) independently arrived at the
same conclusion: it takes `series: Vec<Vec<f32>>` and `labels: Vec<String>`
as **props**, not children — this is not a workaround, it is simply how
charting APIs are built outside of React (ECharts, Chart.js, ApexCharts all
take one config object too). The design sketch (§6) follows the same shape,
which is also this repo's own existing idiom everywhere else
(`SliderProps`, `BarChartProps`-shaped data props, never "reconfigure from
what's nested inside me").

What **does** port with no loss: `ChartConfig` as a plain
`HashMap<&str, SeriesConfig>` → CSS custom properties scoped by a
`data-chart="<id>"` attribute. That mechanism is pure CSS/data and is
completely engine-agnostic — it is the actual, reusable idea worth taking
from shadcn, independent of whatever draws the SVG.

## 2. Accessibility ground truth — recharts, APG, WAI-ARIA Graphics Module

### 2.1 Recharts' `accessibilityLayer`, read from source

Cloned `recharts/recharts` to a local scratch checkout, commit
`86ad3632ff3f83a742001ae6fc079dd27961a2a4` (2026-09-18 — **today**, i.e.
actively maintained; MIT, that checkout's `LICENSE`).

- `src/context/accessibilityContext.tsx` (4 lines, read in full): `useAccessibilityLayer()` reads `state.rootProps.accessibilityLayer`, **defaulting to `true`** when unset.
- `src/container/RootSurface.tsx` (112 lines, read in full): when `hasAccessibilityLayer` is true and the caller hasn't overridden `tabIndex`/`role` explicitly, the root `<svg>` (`Surface`) gets **`tabIndex={0}`** and **`role="application"`** (lines 45–58). It also always receives `title`/`desc` props (rendered as SVG `<title>`/`<desc>` — confirmed by `Surface`'s prop forwarding, not separately re-read since the wiring is directly visible in this file).
- `src/chart/RechartsWrapper.tsx` (`onFocus`/`onBlur`/`onKeyDown`, lines 313–325, read in full): a plain wrapping `<div>` dispatches `focusAction()`/`blurAction()`/`keyDownAction(e.key)` — ordinary bubbling DOM events, no capture-phase trick.
- `src/state/keyboardEventsMiddleware.ts` (221 lines, read in full): on **focus**, if no data point is yet active, index `0` becomes the active tooltip. **ArrowRight**/**ArrowLeft** move the active index by one, **direction-aware** (`selectChartDirection` flips the delta for RTL — this repo's own unbuilt RTL work, per `dev-docs/recommended-implementations.md` §9, would need to thread the same awareness through if it copies this behavior). **Enter** toggles "pinning" the currently-hovered tooltip open/closed. **Blur** clears the active index. Movement is throttled via `requestAnimationFrame` or a configurable delay (`throttledEvents`/`throttleDelay`), not synchronous per keystroke.
- This wiring is **Cartesian-only**: `src/chart/CartesianChart.tsx:18` defaults `accessibilityLayer: true` and forwards it to `RootSurface` at line 75; `PolarChart.tsx` was not found in the `accessibilityLayer` grep at all (grep hit list above), consistent with shadcn's polar demos never passing the prop.

**Editorial note, not from either source:** `role="application"` is a heavy-handed
ARIA escape hatch — it tells assistive tech to stop providing its own
browse-mode navigation and hand every keystroke to the widget's own script.
Modern ARIA authoring guidance treats it as a last resort for exactly that
reason. It is Recharts' own opinion (tier 3 by this repo's own taxonomy,
§2.3), not a standard, and I don't recommend copying it verbatim — see §6.4.

### 2.3 W3C WAI-ARIA Graphics Module — the standards-based oracle candidate

Fetched `https://www.w3.org/TR/graphics-aria-1.0/` directly (W3C
Recommendation, published 2018-10-02) rather than reciting the three role
names from memory:

| Role | Superclass | Accessible name required? | Children presentational? | Use for |
|---|---|---|---|---|
| `graphics-document` | `document` | **Yes** | No | The whole self-contained chart region; can nest |
| `graphics-object` | `group` | No | No | A meaningful sub-part inside a `graphics-document` (e.g. one series, one axis) |
| `graphics-symbol` | `img` | **Yes** | **Yes** | An atomic repeated glyph — a legend swatch is the textbook case |
| (core ARIA) `img` | — | Yes | (implicit) | A single indivisible graphic — **no navigable child content** |

The spec defines **no keyboard interaction at all** — it is a role/semantics
vocabulary, not a behavior pattern (matching this repo's own Tier
1/Tier-2/Tier-3 split: this spec can anchor role/name assertions, but a
keyboard contract on top of it is unavoidably an opinion, same tier as
Recharts' own).

### 2.4 Radix has no chart primitive — confirmed by cloning, not inferred

`radix-ui/primitives` was already available from a local scratch checkout (another
lane); `find … -iname "*chart*"` returns **zero files**. Chart is the one
shadcn/ui catalog entry with no Radix primitive underneath it at all — every
other row in `dev-docs/component-backlog.md`'s table has a Radix primitive
this repo calibrates tier-3 behavior against; Chart structurally cannot,
which is exactly why the task frames the Graphics Module roles as "the
likely oracle basis" instead. `dignifiedquire/dx-components` (this repo's

also has **zero** chart-related files — confirms no adoptable Dioxus port
exists anywhere in the fork network this repo's own backlog research has
already surveyed.

### 2.5 Synthesis — the a11y contract this report recommends

Not `role="application"`. Recommend, in order:

1. **`role="img"` + `aria-label`/`<title>`/`<desc>` on the SVG root** for the
   compact visual (matches the task's own suggestion, and matches the
   Graphics Module's `img` definition: a single indivisible graphic, no
   claim of internal navigability).
2. **A real, visually-hidden `<table>`** mirroring the same series/category/
   value data as the actual screen-reader-facing "browse the data"
   mechanism. A native `<table>` is natively, correctly keyboard-navigable
   cell-by-cell with zero bespoke ARIA-widget behavior to get wrong — this
   is the part of "keyboard-navigable data points" that must work
   correctly for AT users, and it's the one part of this whole feature this
   repo can get for free from HTML semantics rather than invented behavior.
3. **Optional, additive: arrow-key stepping of the visual crosshair/tooltip**
   for sighted keyboard users (mirrors Recharts' actual UX — a keyboard user
   who is not using a screen reader still gets the on-canvas tooltip
   experience). This is tier-3 opinion, cited to Recharts (§2.1), layered on
   top of, never instead of, the hidden table.

This sidesteps `role="application"`'s well-known downside (screen reader
users lose all normal browse-mode navigation the instant focus lands on the
chart) while still delivering everything the task asked for. If a future
implementer wants `graphics-document`/`graphics-object` instead of `img` for
richer internal structure (e.g. a multi-series chart where each series is
its own `graphics-object`), that's a legitimate stronger alternative to
option 1 — flagged as a decision point in §8, not decided here, since AT
support for the Graphics Module roles is still thin in places `role="img"`
is universally supported.

## 4. Per-candidate evidence

### 4a. In-repo pure-RSX SVG engine

No dependency to evaluate — the case for it *is* the case against every
opaque-string candidate (B, D, E) and the case that C is too thin to adopt
(below). It satisfies every constraint in the task brief by the same
construction every other primitive in `primitives/src/` already uses: plain
functions of props producing plain RSX elements, zero `document::eval`,
compiles under the existing `web`-feature cfg axis unchanged
(`scripts/check-cfg-axis.sh` needs no new rule for it — it's the same axis
every primitive already respects). The workspace's existing `palette =
"0.7.6"` dependency (`primitives/Cargo.toml`, already present, used
elsewhere — not a new addition) is available if a future sequential/heatmap
variant ever needs color interpolation; out of MVP scope.

### 4b. `dioxus-charts` 0.4.0 — read in full, not skimmed

Cloned `dioxus-community/dioxus-charts` to a local scratch checkout
(latest commit `01aadb2`, 2026-04-05). `Cargo.toml`: only dependency is
`dioxus` itself (`version = "0.7"`) + `log` — genuinely zero third-party
rendering engine, confirming it's a ground-up RSX implementation, not a
wrapper. Read `src/charts/bar.rs` (492 lines) in full: bars are SVG
`<line>` elements with a thick `stroke-width` (not `<rect>`), grid lines are
real `<line>`s, numeric-axis labels are SVG `<text>`, category labels for
horizontal bars go through `foreignObject` + `<span>` (mixing SVG-native
text and HTML-in-SVG in the same component). Colors: `let mut color_var =
255.0; color_var -= 75.0 * (1.0 / (i + 1) as f32); stroke: "rgb({color_var},
40, 40)"` — a hardcoded red-channel gradient keyed by series index, not a
prop, not a CSS variable, not overridable except by CSS-cascade tricks
against inline presentation attributes. `src/lib.rs`'s module doc
self-describes the whole crate's scope: "PieChart: for Pie, Donut and Gauge
charts; BarChart: for Bar and Stacked Bar charts...; LineChart" — confirmed
against `pie.rs` (`donut: bool` prop exists, line 52) and `line.rs`
(fill is hardcoded `"transparent"`, no area-fill option found). **No
`area`, `radar`, or `radial` chart exists in this crate at all.**
`grep -rn "aria\|role\|tabindex\|onmouse\|onclick\|onfocus\|title {" src/`
returned **zero matches** — no accessibility semantics, no interactivity, no
tooltip, no keyboard handling of any kind, anywhere in the crate.

**Conclusion:** architecturally the right shape (proves RSX-native SVG
charts work fine in Dioxus 0.7), but functionally thin enough that adopting
it doesn't save meaningful work — you'd still write 100% of theming, a11y,
tooltip, legend, and 3 of 6 chart families yourself, while also taking on an
external dependency with a single named maintainer and a ~5.5-month-quiet
repo. The honest comparison is "adopt C and rewrite most of it" vs. "write
it directly," not "adopt C" vs. "build from zero" — and once framed that
way, adopting it adds a dependency for no corresponding reduction in work.
Its `Axis`/`Grid` module shape (`src/grid.rs`) is worth reading as a
reference for the in-repo engine's own scale/tick module, per this repo's
existing "read forks for shape, write original code against house
abstractions" doctrine (`dev-docs/lifting-from-forks.md` §3, already applied
to Command/Resizable/Navigation Menu per `component-backlog.md`) — not
worth vendoring.

### 4c. `charts-rs` 1.0.0

Cloned `vicanso/charts-rs` to a local scratch checkout (latest commit `44a9e81`,
2026-09-12 — the most actively maintained candidate surveyed).
`Cargo.toml`: default dependencies are `arc-swap`, `fontdue` (a pure-Rust
font rasterizer — no `fontconfig`/native font loading), `serde`,
`serde_json`; `resvg`/`image` are gated behind an opt-in `raster` feature
(only needed for PNG/JPEG/WebP/AVIF export, not for SVG generation) — a
genuinely lean, likely-wasm32-friendly default configuration, though this
session did not spend its one scratch-build slot verifying it (spent on
plotters instead, §4d — the more universally-recognized general-purpose
choice). Every chart type exposes `pub fn svg(&self) -> canvas::Result<String>`
(confirmed across `bar_chart.rs`, `line_chart.rs`, `pie_chart.rs`,
`radar_chart.rs`, and 14 more chart-type files) — **one opaque string per
whole chart**, generated in one call, with no children-composition and no
per-element handle for Dioxus to attach an event listener to afterward.
`lib.rs` embeds a default font via `include_bytes!` (adds to binary size;
exact byte count not measured this session). Catalog is enormous — 19 chart
types including several (sankey, sunburst, treemap, theme-river, candlestick)
far outside shadcn's 6-family scope.

**Conclusion:** the most actively-maintained and most capable external
candidate by chart-type count, and its lean default dependency footprint is
a genuine point in its favor over `plotters`. But it shares the decisive
architectural problem every string-output engine has (§4d's analysis
applies identically) — real interactivity and real per-point a11y both
require either re-deriving the same layout math a second time in Dioxus, or
reaching for `document::eval` to inspect the injected markup's DOM after the
fact, which is exactly the "JS-injected DOM" pattern the brief flags as
breaking `oracle/hydration-parity.spec.ts`. Listed as the stronger of the
two "viable but not recommended" options in §5.

output has the exact same opaque-string ceiling as `charts-rs`/`poloto` for
interactivity/a11y/hydration, and it carries the largest transitive
dependency footprint of the three string-output candidates. It does not
out-compete `charts-rs` on any axis except "more people have heard of it";
listed in §5 as a contingency note under option B, not a separate strong
pick.

### 4e. `poloto` 19.1.2

`746dca5`, 2026-04-01, single maintainer). `cargo info` confirms MIT,
minimal listed dependencies. Its own pitch — "outputs SVG and can be styled
using CSS" — is the closest of the string-output group in *spirit* to
shadcn's CSS-variable theming goal (it emits CSS classes onto its generated
markup rather than baking every visual choice into presentation
attributes), and it needs no font-rasterization dependency at all since it
emits `<text>` and lets the consuming browser/engine render glyphs. It is,
however, still one opaque `String` per chart with no per-mark DOM handles,
so the interactivity/a11y ceiling is identical to `charts-rs`/`plotters`,
and its chart-type range is narrower (line/scatter-oriented; a poor fit for
pie/radar/radial without substantial extension). Not selected as a
"viable option" in §5 because `charts-rs` dominates it on chart-type
coverage and maintenance recency while sharing the same architectural
ceiling.

### 4f/4g. `charming` and `plotly` — disqualified on architecture, not on merit

Both wrap a full external JS charting engine (ECharts, Plotly.js
respectively) rather than drawing in Rust. `charming`'s own feature list
(`cargo info charming`) shows `wasm = [serde-wasm-bindgen, wasm-bindgen,
web-sys, js-sys]` and `html = [handlebars]` (HTML-template generation that
embeds the ECharts bundle) — there is no feature combination that avoids
shipping or loading the JS engine. `plotly`'s feature list shows
`plotly_embed_js` (bundles Plotly.js) and `static_export_*` features that
require `plotly_kaleido`/a headless Chromium or geckodriver *at render
time* — incompatible with this repo's SSG build (`dx build --ssg`, a plain
Rust server binary prerender, per `dev-docs/conformance-harness.md`'s
hydration-parity section) even before considering the JS-bundle rule. Both
fail the brief's explicit hard constraint ("no JS bundles are shipped by any
component today") outright, independent of license or maintenance quality
(both are fine on those axes — this is a pure architecture mismatch, not a
quality judgment, same framing this repo's own backlog already uses for
scope-excluded-but-otherwise-good candidates).

## 5. Recommendation

**Option A — build the in-repo pure-RSX engine — is the recommendation.**
It is the only candidate that satisfies every hard constraint in the task
brief *by construction*, using zero new runtime dependencies, and it matches
this repo's own near-universal existing pattern: every primitive under
`primitives/src/` is original composition against house abstractions: none
of them wrap a third-party *rendering or behavior* crate (the two
dependencies that do exist, `palette` for color math and `time`/
`dioxus-sdk-time` for dates, are narrow computational utilities, not
rendering engines).

**Option B (viable, not recommended) — adopt `charts-rs` as a string-SVG
drawing backend**, if the user wants a much larger chart-type catalog sooner
(radar, gauge, and beyond) and is willing to accept: (a) a new
`dangerous_inner_html`-shaped injection technique with zero precedent in
this codebase, needing its own from-scratch verification that Dioxus 0.7's
hydration diffing actually treats it as a safe opaque leaf (unverified this
session — a real, non-trivial risk, not a formality); (b) tooltips/legends
that cannot be real per-point DOM without a parallel, hand-written
coordinate-math layer duplicating whatever `charts-rs` computed internally;
(c) a live dark-mode CSS-variable toggle that requires proving the crate
accepts a raw `var(--x)` token as a color value, not just a resolved hex.
This is a real, defensible option for a team that wants breadth
(sankey/heatmap/treemap/etc.) over depth of integration quality — it is not
a strawman — but it works against three of the four hard constraints the
brief lists (hydration parity, real-DOM tooltips/legends, and, less
directly, the wasm32/no-JS-bundle spirit even though technically no *JS* is
involved here) rather than with them. `plotters` (§4d) is a strictly weaker
version of the same option (same ceiling, heavier wasm32 dependency
footprint, less complete out of the box) — a contingency if `charts-rs`'s
own wasm32 compile ever turns out to be a problem, not a separate pick.

**Option C — fork-and-extend `dioxus-charts` — is dominated by Option A**,
not a distinct third choice. Once you account for what it's actually
missing (all of: theming, a11y, tooltip, legend, area, radar, radial — see
§4b), "adopt C and do that work" and "write it directly against this repo's
conventions" cost approximately the same engineering effort, but only the
second avoids taking on an external dependency maintained by one person with
a ~5.5-month-quiet repository. Recommend reading its `Axis`/`Grid` module
for scale-math shape only, per this repo's own established "read for shape,
never vendor" doctrine — not adopting the crate.

**What this construction subsumes:** every one of the six string-output/
JS-wrapper candidates the task asked to evaluate (charts-rs, plotters,
poloto, charming, plotly) is subsumed by the same finding — real DOM,
required by three of the four stated hard constraints, is unavailable from
an opaque-string or JS-engine architecture regardless of which specific
crate you pick; this is a property of the *category*, demonstrated with a
verified wasm32 build for one member (plotters) and read-source evidence for
the rest, not re-litigated crate-by-crate. **What it does not resolve:**
whether `charts-rs`'s specific wasm32 compile succeeds (inferred, not
verified — flagged in §3/§4c); whether any string-output crate's color
props actually accept a live `var(--x)` CSS token (not checked); the exact
byte cost of `charts-rs`'s bundled font. None of these change the
recommendation, since the disqualifying issue (opaque output, no real DOM)
holds regardless of their answers.

## 6. Design sketch — Option A

### 6.1 File layout

Mirrors this repo's own convention for a multi-piece primitive exactly
(confirmed against `primitives/src/select/` and `primitives/src/combobox/`,
both read via directory listing: `mod.rs` + `context.rs` +
`components/{mod.rs, <piece>.rs...}`, plus a sibling pure-logic file when
there's separable algorithmic work — `select/text_search.rs`,
`color_picker/color_naming.rs`):

```
primitives/src/chart/
  mod.rs                 // re-exports, module docs, ChartKind enum
  context.rs             // ChartContext (ChartConfig, chart id, theme)
  scale.rs               // pure, #[cfg(test)]-unit-tested: linear/band/polar
                          // scale + "nice" tick generation + path-from-points,
                          // arc math (polar_to_cartesian) — same shape as
                          // slider.rs's ordered_range/snap_value/... helpers
                          // and calendar.rs's date-grid math
  components/
    mod.rs
    container.rs          // ChartContainer, ChartStyle-equivalent
    tooltip.rs             // ChartTooltip / ChartTooltipContent
    legend.rs               // ChartLegend / ChartLegendContent
    series.rs                // the per-kind mark renderers (Area/Bar/Line/
                              // Pie/Radar/RadialBar), reading ChartKind

preview/src/components/chart/
  component.json          // cargoDependencies: [] (no new dep), globalAssets
  component.rs             // dx-chart wrapper, merge_attributes, document::Link
  docs.md
  style.css                // --dx-chart-* tokens + dx-chart-* classes
  variants/
    main/mod.rs            // MVP: one interactive Card-wrapped chart
    multi-series/mod.rs    // stage 2+
    tooltip/mod.rs          // stage 2+
    pie-donut/mod.rs         // stage 3+
    radar/mod.rs               // stage 4+
    radial/mod.rs                // stage 5+
```

(Multiple demo variants per component is already this repo's norm, not a
new pattern — `calendar` ships 6, `combobox` ships 4, `date_picker` ships
5, all counted from the live directory tree.)

### 6.2 Public API (data-driven, per §1.4's finding)

```rust
// primitives/src/chart/mod.rs — sketch, not final signatures
pub struct ChartConfig(pub IndexMap<String, SeriesStyle>); // ordered: slot order matters (dataviz skill's fixed-order rule, §6.3)
pub struct SeriesStyle { pub label: Option<String>, pub color: Option<String> } // color: a literal CSS value OR "var(--token)"

pub enum ChartKind { Area, Bar, Line, Pie, Radar, RadialBar }

#[derive(Props, Clone, PartialEq)]
pub struct ChartContainerProps {
    pub config: ChartConfig,
    pub id: ReadSignal<Option<String>>,
    #[props(extends = GlobalAttributes)] pub attributes: Vec<Attribute>,
    pub children: Element, // legend/tooltip/caption slots only — NOT series config (§1.4)
}

// The series/axis data itself is a prop, not nested children:
#[derive(Props, Clone, PartialEq)]
pub struct ChartProps<T: 'static + Clone + PartialEq> {
    pub kind: ChartKind,
    pub data: Vec<T>,
    pub x_key: &'static str,
    pub series_keys: Vec<&'static str>,     // which ChartConfig keys to draw
    #[props(default)] pub stacked: bool,
    #[props(default)] pub show_tooltip: bool,
    #[props(default)] pub show_legend: bool,
}
```

`ChartTooltip`/`ChartLegend` stay as separate, explicitly-rendered pieces
(matching shadcn's own `<ChartTooltip content={<ChartTooltipContent .../>}
/>` idiom) so a caller can customize or omit them — the difference from
shadcn is that they're driven by `Chart`'s own internal hover-index state via
context, not by Recharts' children-introspection.

### 6.3 `ChartConfig` → CSS variables, themed with this repo's own tokens

Read `preview/assets/dx-components-theme.css` in full (323 lines). Two
findings that directly shape this section:

1. **This repo's theme has no categorical color palette at all today** — only
   grayscale `--primary-color-1..7`/`--secondary-color-1..6` and three
   semantic hues (`--primary-success-color` #10b981/#ecfdf5,
   `--primary-warning-color` #f59e0b/#fffbeb, `--primary-error-color`
   #dc2626/#ef4444; `--primary-info-color` reuses the grays). Chart is the
   **first** component in this repo that needs distinguishable series hues,
   so there is no existing token set to simply reuse — new `--dx-chart-1..N`
   tokens are unavoidable, not a style choice.
2. **The light/dark toggle mechanism is a specific, reusable CSS trick**,
   already used for every existing token: `--primary-color-1: var(--dark,
   #0e0e0e) var(--light, #fbfbfb);` paired with `html[data-theme="dark"] {
   --dark: initial; --light: ; }` (and the inverse for light, plus an
   `@media (prefers-color-scheme)` fallback for no explicit `data-theme`).
   New `--dx-chart-N` tokens should follow this exact declaration shape for
   parity with every other token in the file, not invent a second
   convention.

For the actual **hues**, this session ran the `dataviz` skill's own
validator against this repo's real card-surface colors (not the skill's
generic reference surfaces) as live evidence, not a citation of the skill's
own claims:

```
node validate_palette.js "#2a78d6,#eb6834,#1baf7a,#eda100,#e87ba4,#008300,#4a3aa7,#e34948" \
  --mode light --surface "#fbfbfb"   # = this repo's --primary-color-1 light value
  → Lightness band PASS, Chroma floor PASS,
    CVD separation PASS (worst adjacent ΔE 9.1), normal-vision floor PASS (ΔE 19.6),
    Contrast WARN (3 of 8 slots < 3:1 — relief required: visible labels or table view)

node validate_palette.js "#3987e5,#d95926,#199e70,#c98500,#d55181,#008300,#9085e9,#e66767" \
  --mode dark --surface "#0e0e0e"    # = this repo's --primary-color-1 dark value
  → ALL CHECKS PASS (worst adjacent CVD ΔE 8.4, normal-vision ΔE 19.3, contrast all ≥3:1)
```

**Recommendation: adopt this validated 8-hue palette (or its first 5 slots,
mirroring shadcn's own 5 default `--chart-N` tokens) as `--dx-chart-1..N`.**
The one actionable finding from the run: the light-mode contrast **WARN**
(3 slots below 3:1 against a white-ish card) is not dismissable per the
skill's own rule — it obligates a visible relief channel, which this design
already provides for free: a legend is always shown for ≥2 series and the
tooltip always shows a text value next to the swatch (matching shadcn's own
"always render a tooltip label" default and the dataviz skill's own "legend
always present for ≥2 series" rule) — so the WARN is satisfied by the
design's existing shape, not by picking different hues.

`ChartStyle`'s equivalent: instead of Recharts' theme-selector strings
(`""`/`".dark"`), emit both values in the same single-declaration
`var(--dark, …) var(--light, …)` form directly, e.g.:

```css
/* generated once per <ChartContainer data-chart="chart-1">, or simply
   shipped as static tokens in style.css if colors are never per-instance */
[data-chart="chart-1"] {
  --color-desktop: var(--dark, #3987e5) var(--light, #2a78d6); /* --dx-chart-1 */
  --color-mobile:  var(--dark, #d95926) var(--light, #eb6834); /* --dx-chart-2 */
}
```

— i.e. `ChartConfig`'s `color` field can be either a literal value or (more
usefully) `"var(--dx-chart-1)"`, and `--color-<key>` becomes a thin
per-instance alias over the fixed palette tokens, exactly mirroring
shadcn's own `color: "var(--chart-1)"` convention in its demo files
(`chart-bar-default.tsx` line 35, read above).

### 6.4 Accessibility contract (concrete, per §2.5)

- SVG root: `role="img"`, `aria-label` (from a caller-supplied description
  or a generated summary), `<title>`/`<desc>` children.
- A visually-hidden real `<table>` (same visual-hiding technique this repo
  already uses for `.dx-sidebar-sr-only`/`.dx-command-sr-only` — reuse that
  class shape, don't invent a new one) mirroring the chart's own data —
  the actual AT-facing "step through data points" mechanism, native and
  free.
- Legend swatches: `role="graphics-symbol"` + `aria-label` (children
  presentational), per the Graphics Module's own definition (§2.3) — a
  clean fit, not a stretch.
- Optional sighted-keyboard crosshair stepping (Arrow keys move a hover
  index, Enter pins it) — tier-3 opinion cited to Recharts (§2.1), never the
  only navigable path.

### 6.5 Oracle plan

No APG page to vendor (§2.2) and no Radix reference to calibrate against
(§2.4) — this component cannot be a `tier1-apg` or a literal `tier3-radix`
spec by this repo's own existing folder semantics
(`dev-docs/conformance-harness.md`'s three-tier table). Two honest options,
a decision point for §8 rather than decided here:

### 6.6 Primitives/hooks this repo already has to reuse

- **Point-anchored tooltip positioning, not element-anchored.** The chart's
  hover/crosshair tooltip must track a moving pixel position inside the
  plot area, not a fixed trigger element's rect — this is architecturally
  the *same* problem `ContextMenu` already solves, not the same problem
  `Tooltip`/`Popover`/`HoverCard` solve. Confirmed by reading
  `primitives/src/context_menu.rs`: it captures `position: Signal<(i32,
  i32)>` from `event.client_coordinates()` on its trigger's pointer events,
  and renders its content at literal `position: fixed; left/top` (not CSS
  `anchor-name`/`position-anchor`) inside a `popover="manual"` top-layer
  promotion. **Reuse this shape for the chart's data-point tooltip**, not
  `TooltipContent`'s anchor-positioning engine. One specific improvement to
  make while doing so: this repo's own docs already flag that
  `ContextMenu`'s captured coordinates "are never clamped at the point
  they're captured" (`primitives/src/context_menu.rs`'s own doc comment,
  `dev-docs/backlog.md` row 10) — the chart tooltip should close this gap
  by construction (clamp against the plot's own bounding rect) rather than
  reproduce it a second time.
- **Pure, unit-tested math module, same shape as `slider.rs`/`calendar.rs`.**
  Both already separate pure helper functions (`ordered_range`,
  `snap_value`, `closest_thumb_for`, `home_end_target` in `slider.rs`;
  date-grid math in `calendar.rs`) from the RSX components that consume
  them, unit-tested in a trailing `#[cfg(test)] mod tests` block — exactly
  the template `chart/scale.rs` should follow for its linear/band/polar
  scale and "nice tick" math, and exactly the kind of module
  `dev-docs/conformance-harness.md`'s own coverage table already calls out
  as "the algorithmic ones" worth Cargo unit tests, distinct from
  Playwright's job.
- **`merge_attributes` + `dx-<name>` base class + `document::Link` +
  `asset!`** — the exact `preview/src/components/tooltip/component.rs`
  wrapper shape (read in full, §"file layout" above), needs no adaptation.
- **`Card`/`CardHeader`/`CardTitle`/`CardDescription`/`CardAction`/
  `CardContent`/`CardFooter`** already exist verbatim
  (`preview/src/components/card/component.rs`, confirmed) — shadcn's own
  chart demos are 100% `Card`-wrapped; the MVP demo composes this directly,
  zero new primitive needed for the chrome around the chart.
- **`--dx-z-overlay`/`--dx-z-top` and the shared top-layer engine** — the
  chart's tooltip, once promoted via `popover="manual"` per the
  `ContextMenu` shape above, composes correctly with every other open
  overlay on the page for free, the same guarantee every existing overlay
  already has.
