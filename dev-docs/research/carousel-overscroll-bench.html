Carousel Overscroll Bench

Six ways to handle a drag or trackpad swipe past the first or last slide, on the same CSS scroll-snap engine our component uses. Drag each with the mouse and compare. The native control at the bottom has no JavaScript at all — on macOS it is the only one that can show real OS elasticity.

Revision 32 — three lessons from Embla’s trackpad plugin in mode D. Embla’s core has no wheel handling at all; shadcn gets trackpad swipes only from the embla-carousel-wheel-gestures plugin, built on xiel/wheel-gestures (MIT). That plugin takes the input over entirely, which our native-scrolling design forbids, but its detection transfers: a sudden jump during momentum now starts a new gesture at once (re-push knob); deltas are paired before the decay test to smooth jitter; and a momentum ceiling (0.97) keeps a steady slow push from reading as coasting. Those make detection sturdier but barely change how far the band goes; replaying your last session, the band limit does that, so its default is now 0.5 × the width (your hardest flicks: 24–39% → 19–28%).

Revision 31 — a seamless loop. The shipped carousel’s loop rewinds: from the last slide it scrolls back through every slide to the first. shadcn’s loop (Embla) is one endless strip in both directions. The new Seamless loop section below does that with virtual slides from data: 12 items, 5 slides in the page, the window shifting by one each time a move settles. It works for every input at once, including trackpad momentum, and it has no edge, so it needs no rubber-band at all.

Revision 30 — D tuned from your first session. Your Firefox session showed the split working: both flicks from the middle into an edge drew 0px from D, leaving the bounce to Firefox. But the pushes D owns drew 204–465px, 25–58% of the 805px track, for two reasons. Firefox’s wheel deltas are pointer-accelerated (150–590px per event, about 1,500px before your fingers lifted), while WebKit’s curve expects finger travel; a new input gain knob (default 0.3) scales them. And the release test was fooled by jitter while your fingers were down, so it fired about 14 events late; it now waits for smooth geometric decay, which only momentum produces. The knob panel now shows how far your last owned push went.

Revision 29 — mode D, and a correction to the curve every mode used. Two findings from the shipped component on your trackpad. First, the band stacked on top of the platform’s own: you confirmed the browser already rubber-bands this scroller when momentum carries it into an edge (composited, so no script can see it), and B3 drew a second band over it. That double band is the overshoot. D draws a band only where the platform draws none: it decides once, at the start of each gesture, from where the scroller is resting. If the gesture starts away from the edge and scrolls into it, D draws nothing and leaves the bounce to the platform. If the gesture starts already resting at the edge, which the platform leaves dead, D owns the band. Second, the curve. Revision 17 called WebKit’s (1 − 1/(x·c/d + 1))·d “algebraically identical” to our L·x/(x+L) with L = d/c. It is not; they differ by a factor of c. WebKit’s starts at 0.55 px per px and tops out at the track width; ours started at 1:1 and approached 1.8× the width. D uses WebKit’s. B3 is unchanged so you can compare the two directly. D’s knobs are live below the trace, and whatever you settle on is saved with each gesture.

Native control · no JavaScript

Now instrumented — drive this one and it calibrates the others. Identical CSS and no script controls it, but it is watched: every burst records the platform’s own delta curve, whether the OS bounce is visible to JavaScript at all, and — the number that matters most — how long after the last wheel event the motion actually stops. That last figure is the ground truth for “gesture end”, which is precisely what every tuned constant on the other modes is guessing at. Identical CSS, zero script. Scroll it with a trackpad, a wheel, or touch. On macOS and iOS this rubber-bands; on Linux and Windows it does not — which is the second reason the effect is missing, independent of our drag being synthetic.

What to judge

  • Mode D is the proposed port. Judge it on two gestures. A push from rest at an edge should feel like B3 did but stiffer and shorter, because it now uses WebKit’s actual curve. A flick from the middle into an edge should look exactly like the native control below, because D steps aside there. If the owned push still feels off, tune it with the knobs; the values you land on are recorded and become the component’s constants.
  • Your two B2 reports were one defect seen twice, and the recording pins it. The gestures carry scrollStart values of both 0 and 260 — the margin was in a different state at the start of different drags, which is only possible if its removal was racing the next gesture. Several also recorded distinctScrollValues: 0, meaning the finishing bookkeeping for one drag ran after the next drag had already cleared the sample buffer. The damping itself was never the problem: peak raw finger travel reached 960px while visible overscroll capped at 180px, comfortably under the 221px asymptote, and no gesture ever hit the wall. The selection never drifted either — indexStart and indexEnd are 0 on all 30 damped gestures.
  • The trackpad answer costs something, and it is worth being explicit about it. Making the room gesture-scoped is what stops a trackpad coasting into it and getting stuck — your complaint about B. But room that only exists during a gesture is, by definition, not there for the gesture that has not started yet, which is why the wheel needs its own scope rather than inheriting the pointer's. These two requirements pull against each other, and any real implementation has to pick a burst-idle timeout (320ms here). That is a tuning constant, not a construction, and it is the one part of B2 I cannot make self-evidently correct.
  • Your report, confirmed by the recording. B’s peak overscroll came back as exactly 80 on every overdrag — the margin width to the pixel, which is the signature of a hard wall, not of resistance. C’s reached 383–940px with distinctScrollValues: 1, i.e. the track moved several hundred pixels while scrollLeft never changed once. Both of your complaints were the same defect twice: an unbounded input driving a bounded output with nothing shaping the curve between them.
  • B2 fixes the wall by making it unreachable, not by moving it. Raw finger travel goes into rawOver; what the scroll port actually does is limit · x / (x + limit), which asymptotes at 221px against 260px of real room. Every extra pixel of drag buys strictly less than the one before, and the far end is approached but never met — so there is no edge left to hit. Simply lengthening the margin would only have moved the stop further away.
  • B2’s room exists only during a drag. It is installed on the first move past the threshold and removed once the settle has finished, with the scroll port shifted by the same amount so neither transition is visible. Between gestures the space is not there, which is why a trackpad flick cannot coast into it or get stuck — the behaviour you hit on the trackpad in B.
  • C’s escape is fixed by containment, not by stacking. C translates the scroll container, and a transformed scroller carries its own clip box with it — which is why slides painted over the frame. The frame now declares overflow: clip, so nothing inside it can paint beyond it at any transform, under any z-index, in any stacking context. That is a containment rule, so unlike a z-index fix it cannot be outbid by a descendant. clip rather than hidden so the frame never quietly becomes a second scroll container.
  • C’s translation is bounded too, by the same rubber function, at 110px. The clip alone would have stopped the painting while the track still ran arbitrarily far; the two together mean it can neither run away nor escape. Independent guarantees, deliberately — either one failing still leaves the other standing.
  • The objection to C is unchanged. While the transform is applied, the visual position and the scroll position disagree, and the component’s selected-slide tracking reads the scroll position. B and B2 keep one source of truth, which is why I still prefer them despite C feeling closest to native for you.
  • The obvious version of B destroys the component. Adding spacer <div>s instead of margins shifts every slide’s position in container.children — and both the tracking bridge and the drag code read a child’s array position as its slide index. One leading spacer, zero further input, and the selection walks 2→3→4→5 of 5 in about 900ms and locks there, because each misread triggers a scroll that triggers another misread. That is why this bench uses margins on the existing end slides.
  • Estimated cost of shipping B2: 30–50 lines inside the drag bridge, two call sites, no API or component change. The tracking code never learns anything happened.
  • Neither is the OS effect. Compare both against the native control above on your Mac; the real curve is decelerating and rubbery under momentum, while these shape a drag that you are still holding.
