## 1. What the APG reference implementation (our tier-1 oracle) actually does

Read directly from `examples/js/carousel-prev-next.js` and `examples/carousel-1-prev-next.html`:
- **All 6 slides are in the DOM at all times**, in fixed logical order, each `role="group" aria-roledescription="slide" aria-label="N of 6"`. No clones, no virtualization.
- Hidden (non-current) slides are hidden with plain CSS `display:none` on `.carousel-item` (not `.active`) — `carousel-prev-next.css:29-39`. `display:none` removes them from the accessibility tree and tab order in every engine, so this is a clean, unambiguous hide — no `aria-hidden`/`inert` needed on top of it for *this* single-visible-slide design.
- **Next/Previous DO wrap**: `nextCarouselItem`/`previousCarouselItem` do plain modulo index arithmetic — `nextIndex >= length → 0`, `nextIndex < 0 → length-1` (`carousel-prev-next.js:162-176`). So the APG oracle itself treats "wrap to the other end" as normal, unremarked behavior — it is not treated as a special case requiring an announcement beyond the ordinary "k of N" label update.
- Live region: `aria-live` on the slides wrapper toggles `off` while autoplay is running and `polite` once stopped (`updatePlaying()`, `carousel-prev-next.js:194-208`) — exactly the rule stated in the pattern doc (`aria-live=off` if auto-rotating, `polite` if not).
- `prefers-reduced-motion: reduce` forces `paused: true` at construction time (`carousel-prev-next.js:17-21`), before anything else runs.
- Rotation stops on focus-in and on mouse hover (`rotateSlides()` checks `!this.hasFocus && !this.hasHover`), and does not resume without explicit user action.
- Keyboard: no arrow-key slide navigation in the basic variant — only `Tab`/`Shift+Tab` through native `<button>`s; rotation control is first in tab order "so it can be easily located" before the rotating content.
- Tabbed variant (`carousel-2-tablist.html`/`.js`) is structurally identical except slides are `role="tabpanel"` (no `aria-roledescription`) and picked via a `tablist`/`tab` set implementing the Tabs pattern (roving tabindex, arrow keys move between tabs). Crucially: **tabpanel slides can use `aria-setsize`/`aria-posinset`**-free numbering because tabs already carry positional semantics via the tablist; the *basic* (group) variant has to fake it with a literal "N of 6" label because `group` doesn't support `aria-setsize`/`aria-posinset` — the pattern doc says this explicitly (`carousel-pattern.html:142`).

This is a **single-visible-slide, fixed-DOM-order, no-virtualization, always-wraps** design — closest in spirit to none of our three candidates exactly, but it validates two load-bearing facts: (a) wrapping next/prev is the W3C-blessed default, not an edge case to special-message, and (b) "hide the rest" must be real AT/focus hiding, never mere visual displacement.

## 2. WCAG / Understanding docs, condensed

- **1.3.2 Meaningful Sequence**: correct reading sequence must be *programmatically determinable*. Sufficient technique **C27 "Making the DOM order match the visual order"**. Failure **F1**: "changing the meaning of content by positioning it with CSS" (visual reorder without a corresponding programmatic fix). This is exactly the risk in candidate (2): CSS `order` moves slides visually without moving them in the DOM.
- **2.4.3 Focus Order**: focus order must "preserve meaning and operability"; it does **not** have to literally match visual layout (the classic sidebar-after-content DOM/CSS-position example is explicitly allowed) as long as the order stays *sensible*, not "jump around randomly." Failure **F44**: `tabindex` producing an illogical tab sequence. So divergence is not automatically disqualifying — but an order that puts a keyboard-focused, visually-relocated slide in a place that makes no sense (e.g., focus jumps to a slide that is now rendered on the opposite side of the visible window) plausibly is.
- **2.2.2 Pause, Stop, Hide**: auto-advancing carousels are "auto-updating content run in parallel with other content" → must be pausable/stoppable, no time exemption. One shared pause control is enough if several things move.
- **2.3.3 Animation from Interactions (AAA)**: interaction-triggered motion (slide transitions) must be disableable unless essential; `prefers-reduced-motion` is the recommended mechanism (do this even though AAA, since the APG reference implementation itself does it at Level-A-adjacent "best practice").
- **2.5.7 Dragging Movements (WCAG 2.2, AA)**: any drag-to-operate function needs a single-pointer, non-drag alternative (buttons, tap-to-jump, a picker) — our Prev/Next buttons and dot picker already are that alternative for trackpad/touch/mouse drag-to-scroll; just need to confirm they remain present and operable regardless of which loop construction is used.
- **2.4.11 Focus Not Obscured (Minimum, WCAG 2.2, AA)**: a focused component must not be *entirely* hidden by author content. Relevant if a scroll-snap container's `overflow:hidden`/padding could clip a focused slide at the wrap boundary; recommended technique is `scroll-padding`/ensuring focus scrolls fully into view.
- **1.4.13 Content on Hover or Focus**: judged low-relevance (no hover-revealed tooltip content in scope) — not pursued further.

## 3. WAI Tutorials "Carousels"

- Structure: slides "typically best represented as unordered lists"; carousel wrapped in a labelled `<section>`. Note tension with Smashing's advice below (avoid `<ul>` because SR announces total list count including slides hidden via `display:none`/`hidden`, which are excluded from the list count anyway in every engine that treats `display:none` as AT-removal — worth verifying in the concrete build rather than trusting either source blindly).
- Functionality: must be fully keyboard-operable; automatic advance must not steal focus/scroll position from the user; **"Use a WAI-ARIA live region to inform screen reader users what item is currently shown"**, announcing "Item x of y."
- No explicit statement on looping/wrap-around in either the overview or `structure`/`functionality` subpages — the Tutorials are silent on this, leaving APG's reference behavior (wraps, unremarked) as the more authoritative signal.
- `About` section text (both the vendored and live APG pattern) contains the single clearest normative worry for our project: *"the screen reader experience can be confusing and disorienting if slides that are not visible on screen are incorrectly hidden, e.g., displayed off-screen"* — i.e. `position:absolute; left:-9999px` or transform-based "hide" (still in the a11y tree) is explicitly called out as the wrong way to hide a slide. This directly indicts any construction whose "offscreen" slides are still in the accessibility tree.

## 4. Practitioner sources

- **WebAIM** ("Animation and Carousels"): hide inactive slides with `display:none`/`hidden` — nothing else is safe. Warns focus can be "lost" when the focused slide disappears (autoplay ticking under a focused control) — reassign focus to the next slide, or pause on focus, before it disappears. All controls must be real `<button>`. **Overall stance: WebAIM discourages carousels outright** given how often they're built inaccessibly.
- **NN/g**: auto-forwarding carousels are broadly disliked/ignored by users (near-0% interaction with slides after the first), 1s-per-3-words minimum timing if autoplay is kept, disable autoplay on mobile — usability signal reinforcing 2.2.2's pause requirement rather than a new a11y rule.
- **Heydon Pickering, "A Content Slider"**: deliberately **does not loop** — philosophy is native-scroll-first, IntersectionObserver-driven lazy interactivity, offscreen slides get `tabindex="-1"` (removed from tab order) once JS confirms they're not visible, `<ul>/<li>` markup, `role="region"` + `aria-label` + `aria-describedby` on the container. No autoplay at all (sidesteps 2.2.2 entirely by construction — "the fewest bytes of code are the most accessible").
- **Scott O'Hara** (via search synopsis): reference example also disables looping; explicit warning that a looping "Next" that teleports back to slide 1 can produce **focus traps** for the subset of users navigating linearly without noticing they've wrapped.
- **Smashing Magazine (2023 guide)**: put the pause/rotation and prev/next controls *before* the slides in DOM order (matches APG); hide offscreen slides with `hidden`/`display:none`/`visibility:hidden`, explicitly **warns against `<ul>` markup** for slides (contradicts the WAI Tutorial's default list recommendation — flagging the disagreement rather than picking a side, since neither source is decisive on its own and the actual behavior is engine/AT-combination dependent); labels via `aria-roledescription="slide"` + `aria-labelledby`/`aria-label="k of N"`; buttons as the drag alternative (pre-empting 2.5.7).
- **Chrome for Developers, "Make accessible carousels"** (native CSS scroll-snap, i.e. the same base technology as ours): the load-bearing finding for candidate (2). Recipe: **make every slide `interactivity: inert` by default**, then use a **`scroll-state()` container query** to flip only the currently-snapped slide to `interactivity: auto`. This is a state-of-the-art construction that keeps *all* slides in fixed DOM order (no `order` reordering, no clones, no removal from DOM) and instead solves "only the visible slide is focusable/AT-exposed" purely through inertness driven by scroll position — arguably a **fourth candidate** worth flagging to the owner: same DOM-order-always-correct property as candidate (1), same all-slides-present property as candidate (2)/(3), but with zero divergence risk and no virtualization bookkeeping. Caveat: `scroll-state()` container queries are newer than plain `inert` — verify current engine support before treating it as load-bearing (older engines would need a scroll-event/IntersectionObserver fallback that toggles `inert` manually, which is a well-trodden pattern).
- **Cloned-slide bug reports** (via search, multiple independent hits): duplicated `id` attributes break same-page jump-links/`aria-labelledby` references pointing at the "wrong" (or an ambiguous) duplicate node; screen-reader users can arrow past the last real slide into a **duplicate-content clone** with no distinguishing label, which is disorienting in exactly the way APG's About section warns about; voice-control tools (Dragon/macOS Voice Control's "click <name>") that match visible/accessible names become ambiguous when two DOM nodes share an accessible name. Confirms clones are a live, documented failure class, not a theoretical one — matches this repo's CLAUDE.md's own "when the same problem shows up more than once, it's a class" framing, since Slick/Splide/Glide all hit this independently.

## 5. Virtualization-specific guidance

- `aria-setsize` + `aria-posinset` (ARIA spec / MDN): exist precisely for "not all items are in the DOM" (virtualized/lazy lists) so AT can still announce "k of N" without counting DOM children. Only valid on roles that support them (`listitem`, `treeitem`, `option`, `tab`, `menuitem`, `radio`, `row` — **not** the bare `group` role APG uses for slides). This is why APG's basic/group variant fakes the count via a literal `aria-label="N of 6"` string instead of `aria-setsize`/`aria-posinset` — the same fallback candidate (1) must use for its `group`-role slides; if slides instead use `role="tabpanel"`/tabs-pattern picker (the tabbed variant), the positional semantics ride on the `tab` elements, which likewise don't take setsize/posinset either in the APG tabs pattern — so in practice, for this component, **the literal "k of N" accessible-name string is the actually-supported mechanism regardless of construction**, and `aria-setsize`/`posinset` are at best defense-in-depth for AT that happens to support them on `group`.
- General virtualized-list a11y write-ups converge on the same two caveats candidate (1) inherits: (a) content outside the rendered window is invisible to **find-in-page** and to a screen reader's "read from here"/browse-mode linear traversal, since it's simply not present in the DOM; (b) rendering/derendering nodes while they hold focus must be avoided — move focus deliberately first.

## 6. Candidate-by-candidate verdict

### (1) Virtual window (2R+1 slides, re-centred only when idle)
- **Meets by construction**: 1.3.2/2.4.3 (DOM order == visual order always, no CSS trick, no F1/F44 risk ever exists) 4.1.2 (ordinary DOM nodes, ordinary roles).
- **Risk**: virtualization's two generic costs — find-in-page/browse-mode can't reach off-window slides; a window recentre while focus is inside must not run (defer until focus leaves, exactly as APG defers autoplay while focused).
- **Mitigation**: (a) SSR/no-JS renders the *full* slide list in true order (progressive enhancement — the JS-virtualized window is an enhancement over a plain, complete, scrollable list, not a replacement for it); (b) gate re-centring on "no focus inside carousel," matching the reference implementation's autoplay-pauses-on-focus rule; (c) `aria-label="k of N"` using the stable data index (not window position) as the actually-supported positional mechanism (see §5), `aria-setsize`/`posinset` optionally as defense-in-depth.
- No duplicate-id/duplicate-name risk (no clones ever exist).

### (2) All slides in DOM, visual order via CSS `order`
- **Direct risk**: exactly the C27/F1 (1.3.2) and F44 (2.4.3) failure shapes — DOM/tab order and CSS visual order diverge near the wrap point by construction. Whether it's a *conformance failure* in practice depends on whether the divergence "preserves meaning and operability" (2.4.3's actual bar) or "changes the meaning of content" (F1's bar) — plausible reviewer disagreement, i.e. **legal/audit risk even if arguably defensible**, which is worse than a construction with no argument to have in the first place.
- **Mitigation that makes it safe**: don't rely on tab order following `order` at all — make every slide `inert` (or `aria-hidden="true"` + `tabindex="-1"` on every focusable descendant) except the currently-snapped one(s), exactly the **Chrome "scroll-state() + interactivity: inert"** recipe from §4. Because `inert` removes a node from both the tab order and the accessibility tree, the CSS `order` mismatch on every *other* slide becomes moot — AT and keyboard users never reach a slide whose visual position doesn't match its DOM position, only the one slide (or few) that's both visible and interactive, and that one should always be laid out congruently with its own DOM neighbors at the moment it's current. `reading-flow`/`reading-order` (Chrome 137+ only, no other engine yet) can reinforce this for engines that support it but must be treated as a progressive enhancement, never the sole compliance mechanism, given single-browser support today.
- Still no duplicate-id/name risk (no clones), but the *engineering discipline required* — inert boundary must be recomputed correctly on every rotation, forever — is a bigger, easier-to-regress surface than candidate (1)'s "only a few nodes ever exist."

### (3) Clones of edge slides (Slick/Splide/Glide style)
- **Direct, documented risk**: duplicate `id`s breaking `aria-labelledby`/jump-links; duplicate accessible names breaking voice-control disambiguation; a screen-reader user in linear/browse-mode reaching a clone and hearing content indistinguishable from a slide they already visited (the precise disorientation APG's About section warns about, worsened rather than solved).
- **Mitigation**: clones must never have an `id`; must be permanently `inert` (or `aria-hidden="true"` + `tabindex="-1"` on all descendants) — they exist purely as a transient visual bridge, never a settled focus/AT target; the JS "instant scrollTo() teleport back to the authentic node" must complete before any focus/AT dwell time so a user can never linger on a clone; clones must be injected client-side only (never present in SSR/no-JS output).
- Even fully mitigated, this is **the most moving parts for the same end result** as (1): two synchronized DOM copies of edge slides, `id` bookkeeping, and a timing-sensitive teleport-before-dwell requirement layered on top of everything (1) or (2) already need.

## 7. Concrete a11y contract for our seamless loop

- **Container**: `role="region"` or `role="group"` (region if it merits a landmark per the Landmark Regions practice) + `aria-roledescription="carousel"` + `aria-label`/`aria-labelledby` (label must not contain the word "carousel," since the roledescription already supplies it).
- **Slide labels**: `aria-label="{k} of {N}"` (or `aria-labelledby` to a real heading if one exists) where **k is the stable 1-based data index and N is the true total data length** — independent of DOM window position, CSS visual order, or clone status. `aria-setsize`/`aria-posinset` may be added as defense-in-depth but are not sufched on `role="group"`, so the literal label string is the mechanism that actually works everywhere.
- **On wrap**: treat it as an ordinary index change — announce "1 of N" / "N of N" exactly like any other move (matches the APG reference implementation, which does not special-case the wrap with extra copy). Never let a user's screen reader think the list is literally infinite; the k-of-N label re-anchors them every time.
- **Live region policy**: `aria-live="off"` + `aria-atomic="false"` on the slides wrapper while autoplay is running; flip to `aria-live="polite"` the instant autoplay stops (focus entering the carousel, pointer hover, or explicit pause) — do not resume autoplay without an explicit user action.
- **Focus handling on rotation**: never let a virtual-window recentre, CSS-`order` rotation, or clone-teleport occur while focus is inside the carousel in a way that would drop or misplace it. If the focused slide must move/rotate out, deterministically move focus to a stable control (e.g. the just-activated Next/Prev button) rather than letting it fall to `<body>`.
- **Hidden-slide treatment**: any non-current slide must be excluded from *both* tab order and the accessibility tree — use `inert` (single attribute, covers focus + AT + is the Chrome-recommended mechanism for exactly this component) as the default; `aria-hidden="true"` + `tabindex="-1"` on every focusable descendant as a fallback for engines without `inert`. Plain visual displacement (`order`, `transform`, positioning) is never sufficient by itself — this is the literal wording of APG's own About-section warning.
- **Keyboard map**: `Tab`/`Shift+Tab` through native page tab order (rotation control first if present, then Prev/Next, then dot/tab picker if present, then interactive slide content only if the current slide has any); arrow keys reserved for a tablist-style picker (Tabs Pattern roving tabindex) if that variant is used, not for slide-to-slide navigation in the basic/group variant.
- **Rotation control**: present whenever autoplay exists; first in the carousel's tab order; label text toggles between start/stop phrasing (no `aria-pressed`, matching APG's explicit rationale that the changing label itself communicates state).
- **Reduced motion**: `prefers-reduced-motion: reduce` forces autoplay off at initial construction (before anything else runs, matching the vendored reference JS) and forces instant (non-smooth) scrolling for programmatic Prev/Next/dot jumps.
- **Dragging (2.5.7)**: confirm Prev/Next buttons and the dot picker remain present and fully operable by single click/tap regardless of which loop construction is chosen — they are already the required non-drag alternative to trackpad/touch/mouse drag-to-scroll.
- **Focus-not-obscured (2.4.11)**: verify `scroll-padding`/container sizing keeps a focused slide from being clipped by `overflow` at the exact moment a wrap wraps the scroll position.
- **SSR/no-JS fallback**: render the complete, true-order slide sequence with no clones and no windowing when JS hasn't run — the loop/virtualization/clone machinery must be a client-side enhancement layered on top of a fully compliant plain sequence, not a replacement for one.

## 8. Recommendation

**Virtual window (candidate 1)** is the safest default: it is the only construction with *no* argument available against it under 1.3.2/2.4.3 (DOM order is simply always correct, by construction, forever), and it carries none of candidate (3)'s documented, cross-library bug class (duplicate ids/names). Its costs — `aria-setsize`/posinset bookkeeping (or just the literal "k of N" label, which is the mechanism that actually works given `group`'s lack of setsize/posinset support) and a full-list SSR/no-JS fallback — are well-understood, already-solved problems in the virtualized-list-a11y literature, not open design questions.

If the owner wants literally every slide physically in the DOM at once (e.g. for CSS-only architecture reasons), prefer the **Chrome "all slides `inert` by default, `scroll-state()` flips the current one to `interactive`"** construction over raw candidate (2)/CSS-`order`-only: it gets candidate (2)'s "nothing is duplicated" property while sidestepping its actual failure mode, because `inert` — not `order` — is what determines what keyboard/AT users can reach; `order` only ever needs to be visually correct for the currently-interactive slide.

Avoid candidate (3) (clones) unless the owner specifically needs parity with Slick/Splide/Glide behavior; it is the one construction with real, independently-reported field bugs (duplicate `id`/jump-link breakage, voice-control name collisions) rather than theoretical conformance risk, and it adds a timing-sensitive teleport-before-AT-dwell requirement on top of everything the other two constructions already need to get right.
