`dev-docs/research/carousel-2026-09-19.md` §2.1's "trackpad: free (embla)" is wrong. `grep -rn "wheel" packages/embla-carousel/src/components/` and `grep -rln "wheel" packages/embla-carousel/src/` both return **zero matches** at HEAD `85a5e3c`. `DragHandler.ts` (228 lines) only wires `mouseEvents`/`initEvents` via `EventStore` (mouse/pointer/touch) — `research/embla-carousel/packages/embla-carousel/src/components/DragHandler.ts:51-52`. ## wheel-gestures: algorithm, with constants

All in `research/wheel-gestures/src/wheel-gestures/`.

**(a) Gesture segmentation** — `wheel-gestures.ts:200-210` (`updateWillEndTimeout`), `state.ts:7` (`WILL_END_TIMEOUT_DEFAULT = 400`). Not a fixed idle gap: a debounce timer whose length is recomputed every event from the *observed* inter-event spacing: `newTimeout = ceil(deltaTime/10)*10*1.2`, doubled (`Math.max(100, newTimeout*2)`) while momentum hasn't been recognized yet, clamped to `[100, 1000]`ms. `willEnd()` (`wheel-gestures.ts:265-271`) reschedules `end()` on every event with this adaptive value. This is deliberately device-agnostic (comment in `state.ts:1-4`): a slow physical mouse wheel needs a long timeout to stay one gesture; a fast trackpad tightens it once inertia is confirmed.

**(b) User-phase vs. momentum** — `wheel-gestures.ts:144-166, 212-255`, constants in `constants.ts`: `ACC_FACTOR_MIN=0.6`, `ACC_FACTOR_MAX=0.96`, `WHEELEVENTS_TO_MERGE=2`, `WHEELEVENTS_TO_ANALAZE=5`. Raw wheel events are paired up (merge 2 → one "scroll point", summed delta + averaged timestamp) before velocity/acceleration are computed at all — noise reduction the raw per-event stream doesn't get in our design. Per merged point, `accelerationFactor = velocity / previousVelocity` per axis (`wheel-gestures.ts:192`). Once ≥5 such factor samples exist, momentum is recognized (`isMomentum = true`, latched for the rest of the gesture) if **every one of the last 5** satisfies either: both axes decelerate by the *exact same* factor (`sameAccFac`, `<1` and equal — the fingerprint of a browser's own synthetic uniform-decay coast) **or** each axis's factor lies in `[0.6, 0.96]` or is `0` (`accelerationFactorInMomentumRange`, `wheel-gestures.ts:212-216, 233-242`). Native momentum flags (from browsers/OSes that expose one) short-circuit this and are trusted directly (`wheel-gestures.ts:94, 121-124`).

**(c) deltaMode / normalization / axis** — `wheel-normalizer.ts`. `deltaMode` 0/1/2 (pixel/line/page) multiplied by `DELTA_MODE_UNIT = [1, 16*1.125, window.innerHeight]` (`:9-11`). Absolute delta hard-clamped to `±700px` (`DELTA_MAX_ABS`, `:42-49`) against pathological single-event spikes. `reverseSign` is a per-axis `[x,y,z]` boolean array (`:24-40`); Embla's plugin passes `[true, true, false]`.

**(d) Momentum bleeding across gestures** — `wheel-gestures.ts:100-111`. While `state.isMomentum` is true, a new event whose `deltaMaxAbs > max(2, lastAbsDelta*2)` (a real finger repress, not just quieter momentum) — or an explicit native "momentum ended" flag — force-ends the current gesture (`end(true)`, tagged `isMomentumCancel`) and starts a fresh one *immediately*, with no wait for the idle-gap timer. This is a magnitude-jump override, not a time-based one — it is the piece that directly targets "hand touches trackpad again while the previous gesture is still coasting."

**(e) Embla plugin** — `research/embla-carousel-wheel-gestures/embla-carousel-wheel-gestures/src/WheelGesturesPlugin.ts`. Listens `passive: false` (`WheelTargetObserver.ts:11`) and does call `preventDefault()` whenever the dominant-axis delta exceeds config (`wheel-gestures.ts:70-87,96-98`, plugin passes `preventWheelAction: wheelAxis` at `:38`) — it fully owns the input, suppressing native scroll entirely. It drives Embla's own synthetic-drag/transform engine, not native scroll: `wheelGestureStarted()` arms `target.set(location)` (`:62-70`), each event calls `target.add(...)` + `animation.start()` (`:109-129`), and it ends the drag **the instant momentum is recognized** — `if (state.isMomentum) { wheelGestureEnded(); return }` (`:142-145`) — computing a release velocity from the last 170ms of tracked movement and handing off to Embla's own `scrollTo.distance(force, snap)` physics (`:83-101`). Edges/loop: `atBoundary()` respects `engine.options.loop` and clamps at `scrollProgress()` 0/1 (`:103-107`); it implements its *own* manual overscroll resistance (`overBoundaryAccumulation`, delta scaled by `0.25 + progress*0.5`, force-released past `viewSize/2`, `:110-157`) — a hand-built rubber band, independent of any native one, because Embla never touches native scroll position at all. `forceWheelAxis` just overrides which axis/prevent-default is used.

## Comparison to our mode D, ranked recommendations

1. **Adopt the magnitude-jump override for mid-momentum repress (their (d)).** Our mode D only re-arms ownership after a 100ms idle gap; on our own hardware (0.95×/event decay), a repress during still-live momentum can land well inside 100ms and would be missed entirely — a real gap, not a hypothetical. Concretely: while in the "smooth decay" tail, if a new raw delta is `> 2× the previous smoothed delta`, treat it as a new gesture immediately (release the current band / re-derive edge-ownership from current geometry) rather than waiting for the idle timer. Fully compatible with THE RULE — it only changes *when* we stop drawing, never how we write scroll position.

2. **Adopt paired-event merging before ratio comparison (their (b)).** Comparing two-event-merged deltas, not raw per-event deltas, damps single-event jitter that would otherwise flip our "≤ previous and ≥0.8× previous" smooth-decay test. Directly portable; doesn't require owning position via transforms, so none of the "they own position, we can't" caveat applies here.

3. **Tighten our upper decay-ratio bound from 1.0 to ~0.96–0.98 (their `ACC_FACTOR_MAX=0.96`).** Our current `smooth` knob only bounds the ratio from below (≥0.8); their corridor also bounds it from above, which guards against a slow-but-still-actively-driven push (ratio ≈1.0, not decaying) being misread as coast. Cheap, same knob shape.

4. **Do not adopt their release strategy wholesale.** They end the "drag" and hand off to Embla's *own* transform-based physics engine the instant `isMomentum` flips — impossible for us: native scroll-snap momentum *is* our physics engine, and THE RULE forbids writing over it. The transferable idea is narrower: once momentum is recognized, stop *accumulating* further band deflection immediately rather than waiting out the full "3 in a row" window — but given their own window is ~10 raw events (5 merged pairs) vs. our 3, this argues for *not* loosening our run count below 3, and if anything strengthening confidence via recommendation 2 rather than cutting the window.

5. **Consider an input clamp analogous to `DELTA_MAX_ABS=700px` (their (c)) upstream of our `gain` multiplier**, as a hardening measure against pathological single-event spikes (line/page `deltaMode`, unusual hardware) — low priority since our target device is confirmed pixel-mode, but cheap insurance if the component ships beyond the owner's own hardware.

6. **Their adaptive per-gesture timeout (their (a)) does not obviously transfer as-is** — it's tuned for the "should this remain one continuous drag" question in a system that owns absolute position; our idle-gap only decides "should band-ownership be re-derived from geometry," a narrower and cheaper question, so the fixed 100ms (backed by the 64–78ms measured rest) is likely fine for our decision, but is worth re-measuring against a slower mouse-wheel to see if 100ms causes spurious gesture restarts, since their own default (400ms initial) exists specifically for that device class.
