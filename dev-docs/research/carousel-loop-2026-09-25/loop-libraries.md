## Cross-library convergence (the actual finding)

Every library that has *any* a11y layer (Splide, Swiper, Embla+plugin, Flickity,
Slick) — regardless of whether its loop mechanism is clones (Splide, Glide, Slick),
DOM reorder (Swiper), or pure transform/virtual positioning (Embla, Keen Slider's
math, Flickity's `wrapAround`) — converges on the same two rules:

1. **Roving hide/tabindex, not deletion.** Only the current (or focus-containing)
   slide(s) keep `tabindex`/native focusability; everything else — clone or real —
   gets `aria-hidden="true"` and its focusable descendants get `tabindex="-1"`.
   The CSS spec independently codifies the identical shape for scroll-markers.
2. **Don't touch `aria-hidden`/labels while the scroller is mid-motion.** Splide
   explicitly freezes `aria-hidden` during `MOVING`/`SCROLLING` state
   (`Slide.ts:203`) to stop Windows Narrator from reading mid-transit content —
   this is the same "never write/re-read during an active scroll" principle our
   `carousel-overscroll-2026-09-23.md` §3/§6 rule already states, now confirmed
   as convergent, not an idiosyncrasy of our design.

The one library that keeps DOM order fixed and only *moves elements visually*
(Embla, via CSS transform on individual slides) is also the one whose official
a11y plugin most aggressively narrows the tab sequence: **only the active slide's
descendants are tabbable at all**, specifically because leaving the rest tabbable
would expose a mismatch between visual position (transformed) and DOM/tab order
(unchanged). No library was found that reorders *visual* order via CSS `order` /
flexbox while leaving DOM (and thus tab) order untouched and still exposes the full
untouched tab order to the user — the moment visual and DOM order diverge, every
library found here responds by shrinking the tab-reachable set down to "just the
current slide", not by trying to reconcile the two orders.

Swiper is the only library that reorders **DOM** order (real nodes, not visual-only)
and is also the only one with a documented, dedicated keyboard-trap bug+fix
(`a11y.ts` `handleTabKey`, issue #8181): because DOM order changes but the set of
real nodes doesn't shrink, Tab from the edge would otherwise cycle forever inside
the widget; Swiper's fix is a one-keypress `inert` on all but the current slide so
focus escapes to the next real page element.

## Evaluation of our three candidate constructions

**Ranking: (1) virtual 2R+1 window > (2) CSS `order` visual rotation > (3) clones.**

- **(1) Virtual window, re-centred only when idle** — closest in shape to Embla's
  transform-based real-slide repositioning and to Keen Slider's/Flickity's modular
  index math: DOM node count stays bounded and *constant*, no duplicate ids, no
  duplicate ARIA labels, and because re-centring only happens at idle it
  automatically satisfies the "never touch position/attrs while scrolling" rule
  that Splide had to special-case (`Slide.ts:203`) and our own design doc already
  requires. "N of M" and focus stay well-defined at all times because the data model,
  not the DOM, is the source of truth for the real index — exactly how Swiper's
  `data-swiper-slide-index` and Embla's `getAriaText` decouple label text from
  transient DOM/visual position. This is the only one of the three with a direct,
  working precedent for *native-scroll* carousels (Keen Slider, Flickity) rather
  than JS-transform ones (Embla) — meaningful since we're on real `scroll-snap`,
  not a transform-driven track.
- **(2) CSS `order` visual rotation, DOM order fixed** — no library studied does
  this for slide content, and Embla's experience with the nearest analogue
  (transform-only visual movement, DOM order fixed) is that its accessibility layer
  had to *forbid* Tab from following DOM order at all once visual ≠ DOM order,
  collapsing to "only the current slide is tabbable." That is a workable fallback
  for us too, but it forfeits "Tab through all slides" as a supported interaction
  and requires auditing that our reading-order/roving-tabindex logic never lets a
  hidden-by-`order` slide keep a stale `tabindex="0"` — an easy class of bug to
  reintroduce by accident (which is exactly the a11y-bug list above: Glide and
  Keen Slider ship with *zero* tabindex hygiene, and that omission is what's
  usually called an "a11y bug" in the wild).
- **(3) Clones** — is what most of the ecosystem defaults to (Splide, Glide, Slick)
  precisely because it's the least invasive to write, but it is also the
  mechanism carrying the most citable, fixed-after-the-fact bugs: Slick's
  `.clone(true)` duplicates *bound event handlers*, not just markup (`slick.js:2455`),
  a real footgun for any interactive (button/input-bearing) slide content in a
  Dioxus vdom world where the framework, not the library, owns node identity and
  diffing — clones fighting the vdom's own reconciliation is a second, independent
  reason to avoid this path for us specifically. Splide is the most careful of the
  clone-based libraries (clones never receive semantic attributes at all, rather
  than receiving-then-stripping them), which is the bar to clear if clones were
  chosen, but still requires permanently growing the DOM and keeping two numbering
  schemes (`index` vs `slideIndex`) in sync (`Slide.ts:95,152,242,274`).
